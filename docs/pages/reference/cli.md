WeaveC is one tool, `weavec-cc`: Clang's compiler driver with WeaveC inside. It guards every memory access of the C and C++ code it compiles and links the runtime that the guards call; `weavec-c++`, a link to it, is its C++ driver, as `clang++` is Clang's. The options below are specified by [RFC 0035](/rfcs/0035-guard-by-default/) §7 as amended by [RFC 0036](/rfcs/0036-deterministic-heap-reuse/) §1, §6 and §7, [RFC 0039](/rfcs/0039-cxx/) §1, [RFC 0040](/rfcs/0040-actionable-reports/) §8, and for Safe C by [RFC 0041](/rfcs/0041-safe-c/), [RFC 0042](/rfcs/0042-typed-memory/) and [RFC 0043](/rfcs/0043-ownership/) §1, §11 and §12; `weavec-cc --help-weavec` lists the ones your build accepts.

## Invocation

```sh
weavec-cc [clang options] [weavec-cc options] source.c -o program
weavec-c++ [clang options] [weavec-cc options] source.cpp -o program
make CC=weavec-cc CXX=weavec-c++
```

`weavec-cc` accepts every Clang driver option, so a build system uses it as it would use `cc`, and `weavec-c++` as it would use `c++`. Invoked as `weavec-c++` (or with `--driver-mode=g++`) the driver is in Clang's C++ mode: `.c` sources compile as C++, and a link adds the C++ standard library (`-lc++` on Darwin, `-lstdc++` on Linux, as `-stdlib=` says). `weavec-cc file.cpp` compiles C++ but, as `clang` does, links without the C++ library.

An unknown `-fweavec-*` flag is an error. Every other flag is Clang's. When WeaveC is on, the driver defines `__WEAVEC__=1` and puts the directory of `weavec.h` on the system include path. `weavec-cc --version` prints Clang's version block first, then `weavec-cc version <version> (<revision>)`, the LLVM it was built with, and the runtime's interface version and the platform (`runtime ABI 44, for arm64-apple-darwin…`), so a configure script that reads the first line sees Clang. Clang's headers and builtins are those of the toolchain (`lib/clang/<major>` beside `bin/`). Assembly sources (`.s`, `.S`) and `-save-temps` compiles are assembled by the system assembler (`as`), since Clang's integrated assembler is not part of `weavec-cc`. On macOS a link with `-flto` uses the libLTO of the LLVM `weavec-cc` is built with, which the toolchain carries as `lib/libLTO.dylib`. Response files (`@file`) are expanded first, as Clang's driver does. C++ and Objective-C compiles get every Clang action but the static analyzer, the rewriters and plug-ins.

C and C++ sources are guarded alike. Objective-C, Objective-C++, OpenCL and CUDA sources are compiled as Clang compiles them, without guards; so is everything under `-fno-weavec` or `-fweavec-checks=none`.

### Debug information

So that every frame of a [report](#reports) names its file and line, a compile in an enforcing mode emits line tables (as `-gline-tables-only` does, with inlined calls and columns) when its command line asks for no debug information; any `-g` keeps its level, and a command line whose last debug option is `-g0` gets none (a report's frames then name functions only). It keeps the names of locals (`-fno-discard-value-names`), which a stack report prints, and on x86-64 Linux it keeps frame pointers (`-fno-omit-frame-pointer`) unless the command line says `-fomit-frame-pointer` last; the runtime unwinds stacks by their frame records. On Darwin, where the line tables stay in the object files, a compile and link in one step writes a `.dSYM` bundle next to the program, as `clang -g` does; a program linked from objects keeps the objects' paths, so leave them in place or run `dsymutil` on the program.

### Fortification and the C++ libraries' checks

On glibc targets, an optimizing compile in an enforcing mode whose command line neither defines nor undefines `_FORTIFY_SOURCE` gets `-D_FORTIFY_SOURCE=3`, so that the C library's headers pass each string and `printf`-family call the size of the object or field it writes; the guards check that size ([guarantee (F)](/reference/guarantees/#the-guarantee)). A command line that sets its own level, `-D_FORTIFY_SOURCE=0` included, keeps it. Darwin's SDK fortifies optimizing compiles at level 2 by itself.

A C++ compile in an enforcing mode gets `-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST` and `-D_GLIBCXX_ASSERTIONS` (each C++ library ignores the other's), unless its command line defines or undefines `_LIBCPP_HARDENING_MODE`, `_GLIBCXX_ASSERTIONS` or `_GLIBCXX_DEBUG`: the C++ library's own bounds checks of `operator[]`, `front`, `back`, `span`, `string_view` and `optional`. A failed check is reported as [`library-assertion`](#check-modes) at the line that called the library.

### AddressSanitizer compatibility

By default, in the enforcing modes, `weavec-cc` parses each C unit as AddressSanitizer would: `__SANITIZE_ADDRESS__` is defined, `__has_feature(address_sanitizer)` is true and `no_sanitize("address")` is accepted. AddressSanitizer's own instrumentation never runs. Code written to be clean under ASan, such as a pool allocator that poisons its free space with `ASAN_POISON_MEMORY_REGION` or a scan that reads past an object only when ASan is off, is then clean under WeaveC. On Darwin, where Clang turns fortification off under ASan, the SDK's fortification stays on.

The runtime implements ASan's poisoning interface with ASan's meaning: `__asan_poison_memory_region` (whole 16-byte granules inside the region become not addressable, and an access to them reports `use-after-poison`), `__asan_unpoison_memory_region`, `__asan_address_is_poisoned`, `__asan_region_is_poisoned` and `__asan_describe_address`. It implements the container annotations the C++ libraries call (`__sanitizer_annotate_contiguous_container`, `__sanitizer_annotate_double_ended_contiguous_container`, and the `verify` and `find_bad_address` queries): a `std::vector`'s or `std::deque`'s storage past its elements is not addressable, and an access to it reports `container-overflow`. It accepts and ignores `__asan_handle_no_return`, the fake-stack queries (there is no fake stack), `__sanitizer_print_stack_trace`, `__sanitizer_set_report_path`, the fiber-switch hooks, and LeakSanitizer's `__lsan_*` entry points (there is no leak checking).

`-fno-weavec-asan-compat` keeps the language options as the command line set them, for code whose ASan paths call a sanitizer interface the runtime does not implement (a link error) or behave differently in a way the program does not want. A unit built with a sanitizer of its own (`-fsanitize=address` and the like) is [built without the runtime](#the-runtime).

## Check modes

| `-fweavec-checks=` | A failed guard or index check                      | Guards removed by a local rule | Zero-init default | Runtime    | Guarantee                     |

| `trap` (default)   | prints a report and traps                          | removed                        | on                | linked     | yes                           |
| `report`           | prints a report once per site; the program goes on | removed                        | on                | linked     | only with `WEAVEC_RT_ABORT=1` |

A trap ends the program with `SIGTRAP`, or `SIGILL` on x86-64. Before it traps, the runtime unblocks both signals in the failing thread and resets a disposition the program set to ignore them, so the program ends even with the signals blocked; a handler the program installed still runs. First it prints a [report](#reports) on stderr.

### Reports

Every report has the same shape ([RFC 0040](/rfcs/0040-actionable-reports/) §5): a first line that names the failure, the stack of the access, a paragraph for each object the runtime can place the address in, and a summary line:

```text
weavec: heap-buffer-overflow at vec.c:9:43: read of 4 bytes at 0xc080000010
    #0 0x1041e0853 in get vec.c:9
    #1 0x1041e0aeb in main vec.c:15
    #2 0x19b523e7f in start (/usr/lib/dyld+0x31e7f)
weavec: 0xc080000010 is 0 bytes after the 16-byte heap object at 0xc080000000, allocated by thread T0:
    #0 0x1041e095b in main vec.c:12
    #1 0x19b523e7f in start (/usr/lib/dyld+0x31e7f)
weavec: summary: heap-buffer-overflow at vec.c:9:43 in get (thread T0)
```

- **The first line**, `weavec: <kind> at <file>:<line>:<col>: <what>`, names the kind, the source location of the access (`<unknown>` when the unit has none), whether it reads or writes, its width and its address; an access with no known width reads `access at 0x…`.
- **The stack** of the access follows, at most 32 frames, each indented four spaces as `#<n> 0x<pc> in <function> <file>:<line>:<col>`, starting at the function that made the access. An inlined call repeats the frame number of the function it was inlined into, innermost first. On Darwin `atos` gives no column. A frame with no line table (a system library, a unit compiled with `-g0`) reads `in <function> (<module>+0x<offset>)`, which [`weavec-cc --weavec-symbolize`](#symbolization) can name later.
- **Object paragraphs** start with `weavec: 0x… is …` and place the address relative to the object it is in or nearest: a heap block with the stacks that allocated and released it, a local with the frame's other locals, a global with its definition. The kinds table below gives each one's form.
- **The summary line**, `weavec: summary: <kind> at <location> in <function> (thread T<n>)`, repeats the kind and the location and names the innermost function and the thread, for a reader that searches a log. Threads are numbered in the order the runtime first sees them, the main thread `T0`; a named thread prints its name too (`T3 'worker'`).

### Bad releases

The allocator checks every release, from WeaveC's code or any other, and stops the program at one it cannot honor, in every mode, since it cannot go on from one. The release forms are `free`, `realloc`, `operator delete` and `operator delete[]`; the allocator records which form allocated each block (`malloc`, `operator new` or `operator new[]`, RFC 0039 §4), so `delete` of `new[]`, `free` of `new`, and `delete` or `realloc` of `malloc`'s are mismatches, and so is a sized `delete` through a base without a virtual destructor. A call of `free`, `realloc`, `reallocf`, `reallocarray` or an `operator delete` form in a guarded unit passes the call's location; a release through a function pointer, from unguarded code or from the C library is located at its stack's first frame, without a column (`weavec: double-free at f.c:14: free of 0x…`), or `<unknown>` when no frame has a line. On Darwin the releases the system's own libraries make are not checked, since they mix forms themselves.

```text
weavec: double-free at cases.c:7:48: free of 0xbd80000000
    #0 0x1042d8977 in drop cases.c:7
    #1 0x1042d8a63 in main cases.c:12
    #2 0x19b523e7f in start (/usr/lib/dyld+0x31e7f)
weavec: 0xbd80000000 is the 8-byte heap block at 0xbd80000000, released by thread T0:
    #0 0x1042d8977 in drop cases.c:7
    #1 0x1042d8a5b in main cases.c:12
    #2 0x19b523e7f in start (/usr/lib/dyld+0x31e7f)
weavec: the block was allocated by thread T0:
    #0 0x1042d8a4f in main cases.c:12
    #1 0x19b523e7f in start (/usr/lib/dyld+0x31e7f)
weavec: summary: double-free at cases.c:7:48 in drop (thread T0)
```

### Report and verify modes

In report mode each failing site (kind, file, line and column) prints its report once and the program continues, with no guarantee; a bad release still stops it. Verify mode is the monitor of the removal rules: every guard a local rule removed is emitted too, and its failure prints `weavec: weavec.proven: <kind> at …` before the trap, which means WeaveC removed a guard it needed. Verify mode does not version loops.

### Symbolization

The runtime records the stack of every allocation and release (8 frames each by default, every unique stack stored once; `WEAVEC_RT_HEAP_STACKS=<n>` keeps `n` frames, at most 32, and `0` records none, and the paragraphs then say `(not recorded: WEAVEC_RT_HEAP_STACKS=0)`). When a report needs them, it names the frames by running a symbolizer that reads the modules' line tables: on Linux `weavec-cc --weavec-symbolize`, found beside the runtime's library (`<prefix>/bin/weavec-cc` for `<prefix>/lib/weavec/libweavec_rt.so.<abi>`), started once and kept; on Darwin `/usr/bin/atos`, which reads the debug map that links a program to its objects' line tables, or `weavec-cc` when `atos` is missing or fails. `WEAVEC_RT_SYMBOLIZER=<path>` names another program that speaks `llvm-symbolizer`'s protocol (`CODE <module> 0x<offset>` lines in, function and `file:line:column` lines out). A symbolizer gets five seconds for a report's frames. A set-user-ID or set-group-ID program runs none, and neither does a program under `WEAVEC_RT_SYMBOLIZE=0`: a frame then reads `in <function> (<module>+0x<offset>)`, with the function the dynamic loader names (the nearest symbol it knows).

Such frames can be named later, on a machine with the same binaries, from a report log or a CI artifact:

```console
$ WEAVEC_RT_SYMBOLIZE=0 WEAVEC_RT_REPORT_LOG=reports.log ./vec 4
$ weavec-cc --weavec-symbolize reports.log
weavec: heap-buffer-overflow at vec.c:9:43: read of 4 bytes at 0xbc80000010
    #0 0x1025c4853 in get /src/vec.c:9:43
    #1 0x1025c4aeb in main /src/vec.c:15:18
    #2 0x19b523e7f in start (/usr/lib/dyld+0x31e7f)
...
```

It prints the logs with each such frame rewritten and the rest of their lines as they were.

## The runtime

The runtime is one shared library, `libweavec_rt.so.<abi>` on Linux (soname `libweavec_rt.so.<abi>`) and `libweavec_rt.<abi>.dylib` on Darwin (install name `@rpath/libweavec_rt.<abi>.dylib`), so that a program never loads a runtime of another ABI, in the toolchain's `lib/weavec`. It holds the shadow memory, the arena allocator with `malloc`, `calloc`, `realloc`, `free` and the other standard allocation functions and C++'s `operator new` and `operator delete` in all their forms, the sweep, the guards' slow paths, the checked library wrappers, ASan's interface and the reports, and exports only those. Every link in the `trap`, `report` and `verify` modes, of a program, a shared library (`-shared`, `-dynamiclib`) or a plug-in (`-bundle`), adds the library before the first library on the line, an rpath to its directory (or to [`-fweavec-rpath`](#weavec-cc)'s), the runtime's archive `libweavec_rt.a`, and `-lpthread` on Linux. The link takes nothing from the archive; it is there for a link another driver makes from what it reads in this one (CMake links a target with C and C++ sources with `c++`, adding the C compiler's libraries), whose program then carries the runtime itself. The archive is never loaded whole: inside `-Wl,--whole-archive` the driver closes the region around it, and under `-Wl,-all_load` it leaves the archive out. A static Linux program (`-static`, `-static-pie`) takes the archive `libweavec_rt.a` instead, with no rpath; a static C++ program also gets `--wrap=` for the unwinder's `_Unwind_RaiseException` and `_Unwind_Resume_or_Rethrow` and `__cxa_begin_catch`, which the runtime stands in front of (elsewhere it interposes them) to mark the frames an exception unwinds. A relocatable link (`-r`) gets nothing. Link through `weavec-cc` so that it can add the library; a link by another driver fails with undefined `__weavec_rt_` symbols. [Safety guarantees](/reference/guarantees/) states what the guards promise.

Every image a process loads that `weavec-cc` linked depends on the library, so the dynamic loader loads it once, before them, and one runtime serves the process: one shadow, one heap, one quarantine, whatever the images' version scripts, `-Bsymbolic` or link order. On Linux the library comes before the C library in the loader's search order, so its `malloc` serves every image and the C library's own allocations (`strdup`, `getline`, `asprintf`); on Darwin the images `weavec-cc` linked bind to its allocator and the rest of the process reaches the arena through its malloc zone. A program that runs a guarded image elsewhere (on another machine, from a package) needs the library too, as a program built with ASan's dynamic runtime does: install it beside the program and link with `-fweavec-rpath='$ORIGIN'` (Linux) or `-fweavec-rpath=@loader_path` (Darwin).

When a program that `weavec-cc` did not link loads a guarded shared library on Linux (a Python extension, a PostgreSQL module), the C library's allocator was bound first and keeps the process's heap; the runtime leaves it alone, checks the guarded image's frames and globals, and says once that the heap is not:

```text
weavec: note: the program's allocator is not WeaveC's (/lib/x86_64-linux-gnu/libc.so.6 serves it: the program was not linked by weavec-cc): heap accesses are not checked; preload <toolchain>/lib/weavec/libweavec_rt.so.44 to check them
```

`LD_PRELOAD=<toolchain>/lib/weavec/libweavec_rt.so.44` makes the runtime the process's allocator from the start; `WEAVEC_RT_NOTES=0` silences the note. Images built by two WeaveC versions (two runtimes of different interface versions) cannot share a process, which stops at the second one's load with:

```text
weavec: error: two WeaveC runtimes in one process (<first> and <second>): build every image with one weavec-cc
```

`weavec-cc` compiles without guards and links without the runtime, as if `-fweavec-checks=none` had been given, when the command line has `-ffreestanding`, `-nostdlib`, `-nodefaultlibs` or `-nolibc`, a sanitizer that replaces the allocator (`-fsanitize=address`, `hwaddress`, `memory`, `thread`, `leak` or `kernel-address`), or a target other than 64-bit Darwin or Linux. A link prints one of:

```text
weavec-cc: note: building without the WeaveC runtime (-fsanitize=address replaces the allocator): memory accesses are not guarded
weavec-cc: note: building without the WeaveC runtime (-nostdlib links no C library): memory accesses are not guarded
weavec-cc: note: building without the WeaveC runtime (-ffreestanding has no hosted C library): memory accesses are not guarded
weavec-cc: note: building without the WeaveC runtime (the runtime supports 64-bit Darwin and Linux targets): memory accesses are not guarded
```

When a link input, an object or a member of an archive, defines `malloc` itself, the program keeps its allocator: the loader binds `malloc` to the program's definition before the runtime's. The guards stay, but the heap is untracked:

```text
weavec-cc: note: 'alloc.o' defines the allocator, which serves the program instead of the WeaveC runtime's: the heap is untracked, guards pass on it and releases are not validated
```

A program's own definition of another allocation function (`posix_memalign`, `reallocarray` and the like) over `malloc` replaces the runtime's and keeps the arena. A `free` that reaches the runtime's allocator from code another compiler built is still validated.

A released block is reused only after a _sweep_ finds no pointer to it ([guarantee (T)](/reference/guarantees/#the-guarantee)). A sweep stops every other thread of the process, scans the threads' registers (vector registers too), stacks and thread-specific data, every readable mapping of the process but code and shared files it cannot write, and every live heap block for words that point into released blocks, and returns the blocks nothing points to to the free lists; blocks something still points to stay released until a later sweep. With 64 MiB or more of live heap the sweep's mark is shared with up to seven worker threads of the runtime's (one fewer than the processors), which are never stopped and hold no program pointer. It runs when the bytes released since the last sweep exceed `WEAVEC_RT_QUARANTINE` and a quarter of the live heap (the soft budget) and the last sweep ended at least eight of its durations ago, so that sweeps take at most about a ninth of the run time while the hard budget is not reached; when they exceed twice `WEAVEC_RT_QUARANTINE` and half the live heap (the hard budget), at once; and when a size class runs out of space after a quarter of its region was released into it (otherwise the class takes a spare region). Between sweeps the released memory waits. Each thread keeps up to 32 free and 32 released slots of each small size class to itself; the released ones are quarantined as any other and join the shared quarantine when the thread's cache fills, when it sweeps, and when it exits. On Darwin the sweep stops threads with `thread_suspend`; on Linux it signals each thread. The sweeping thread blocks signals while it runs, so that a handler that allocates does not wait for the sweep it interrupted.

| Environment variable           | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WEAVEC_RT_QUARANTINE=<bytes>` | The bytes of released blocks, gathered since the last sweep, that may start a sweep once they also exceed a quarter of the live heap; twice as many, and half the live heap, start one at once. Default 64 MiB (67108864). A smaller value sweeps more often and holds less memory; no value lets a block be reused without a sweep.                                                                                                                                                                                                    |
| `WEAVEC_RT_SWEEP_SIGNAL=<n>`   | Linux only: the signal number the sweep stops threads with. By default `SIGPWR`, or `SIGXCPU` when the program handles `SIGPWR`.                                                                                                                                                                                                                                                                                                                                                                                                        |
| `WEAVEC_RT_SWEEP_THREADS=<n>`  | The mark workers a sweep of a large heap uses, at most 7; `0` marks on the sweeping thread alone. By default one fewer than the processors, up to 7.                                                                                                                                                                                                                                                                                                                                                                                    |
| `WEAVEC_RT_FAULTS=0`           | Install no handlers for `SIGSEGV` and `SIGBUS`, so that a fault the shadow did not see is not reported as `memory-fault`. The handlers are installed only where the disposition is the default, and a handler the program installs replaces them.                                                                                                                                                                                                                                                                                       |
| `WEAVEC_RT_ABORT=1`            | In report mode, trap at the first failure as trap mode does.                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `WEAVEC_RT_CONTAINERS=0`       | Ignore the C++ libraries' container annotations, so that no access reports `container-overflow`: for a program that links a unit built without them that changes a standard container's size. A program with a fast safe unit (RFC 0045) ignores them unless `WEAVEC_RT_CONTAINERS=1`.                                                                                                                                                                                                                                                  |
| `WEAVEC_RT_REPORT_LOG=<path>`  | Append every report to this file instead of printing it on stderr, so a test that captures stderr sees only the program's own output. Ignored by set-user-ID and set-group-ID programs.                                                                                                                                                                                                                                                                                                                                                 |
| `WEAVEC_RT_REPORT_FORMAT=json` | Write each report as one line of [JSON](#json-reports) instead of text.                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `WEAVEC_RT_SYMBOLIZE=0`        | Run no [symbolizer](#symbolization): a report's frames name their module and offset, and the function the dynamic loader knows.                                                                                                                                                                                                                                                                                                                                                                                                         |
| `WEAVEC_RT_SYMBOLIZER=<path>`  | The symbolizer to run instead of `weavec-cc` (Linux) or `atos` (Darwin): a program that speaks `llvm-symbolizer`'s protocol, such as `llvm-symbolizer` itself.                                                                                                                                                                                                                                                                                                                                                                          |
| `WEAVEC_RT_HEAP_STACKS=<n>`    | Frames of each allocation and release stack: 8 by default, at most 32; `0` records none. A heap report then says `(not recorded: WEAVEC_RT_HEAP_STACKS=0)` where the stacks would be. Recording costs a program that allocates and releases at a high rate some of its CPU time; a program with a safe unit records none unless the variable asks, and a heap report from a fast safe program ends with `weavec: note: built for speed; rebuild with -fweavec-safe-checks=full for allocation stacks and exact use-after-free reports`. |
| `WEAVEC_RT_STATS=1`            | At exit, print the runtime's counters on stderr, one per line, as `weavec: runtime: <n> <what>`. The process's one runtime counts every image's work.                                                                                                                                                                                                                                                                                                                                                                                   |
| `WEAVEC_RT_NOTES=0`            | Do not print the note that the process's allocator is not the runtime's.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

The counters of `WEAVEC_RT_STATS=1` are allocations, releases, recycled slots (released slots a sweep returned for reuse), huge blocks, slow guards (the guards whose inline check sent them to the runtime), range guards, string guards, stack unpoisons (clearings of the stack's shadow before a call that does not return) and sweeps. Then come the sweeps' total and longest pause and what the last sweep had to keep; the most the live heap's slots and the released blocks waiting for a sweep held; the unique stacks the runtime recorded for allocations and releases, and their memory; and the writable memory, at exit, that neither the runtime nor a thread's stack accounts for:

```text
weavec: runtime: sweeps took 48 ms (longest 7 ms); the last retained 0 blocks (0 bytes)
weavec: runtime: at most 86 MiB of live slots and 82 MiB of released ones waiting for a sweep
weavec: runtime: 5210 stacks recorded (1342 KiB)
weavec: runtime: 480 MiB of writable memory the runtime does not track (mappings the program or its libraries made: objects an allocator of their own carves from them are not checked)
```

A large figure on the last line is the sign of a program that carves objects out of memory it mapped itself (its own allocator, a pool, an arena): accesses inside that memory are not checked against the objects in it.

The counters are not synchronized between threads.

## Ledger and summary line

The enforcement ledger records what the guard passes decided for each access of a unit. It is JSON, `weavec-ledger` version 7:

```json
{
  "schema": "weavec-ledger",
  "version": 7,
  "producer": { "name": "weavec-cc", "version": "0.16.0" },
  "units": [
    {
      "source": "lookup.c",
      "object": "lookup.o",
      "target": "arm64-apple-macosx15.0.0",
      "config": { "checks": "trap", "zeroInit": true },
      "summary": { "accesses": 3, "proven": 1, "guarded": 2, "unguarded": 0 },
      "functions": [
        { "function": "lookup", "tier": "guarded", "owns": false, "file": "lookup.c", "line": 6 }
      ],
      "fields": [],
      "rows": [
        {
          "function": "lookup",
          "display": "lookup",
          "file": "lookup.c",
          "line": 8,
          "column": 12,
          "operation": "load",
          "bytes": 4,
          "outcome": "guarded",
          "reason": "access"
        }
      ]
    }
  ]
}
```

`functions` lists each function the unit defines outside system headers with its tier, `safe`, `guarded` or `unsafe` (or `unsettled`: a safe function too large for ownership's dataflow to settle, whose owners are not checked and which the audit lists as trusted), and `owns`, true when a parameter or the result is `WEAVEC_OWNED` (RFC 0042 §10, RFC 0043 §11); a safe function's body is the symbol `<name>.weavec.safe` in rows. `fields` lists each pointer field of the structs the unit defines, as `{"record", "field", "kind", "file", "line"}` with `kind` `owner`, `reference` or `borrowed`, and, with `kind` `global`, each global owner a safe function reads in place (`record` is the function, `field` the global). A row's `function` is the function's symbol and `display` its name demangled (a C++ function's `_ZN5table4findEi` is `table::find(int)`; a C function's is its own). Its `operation` is `load`, `store`, `rmw` (an atomic operation), `copy`, `set`, `lane` (a lane of a masked or gathered access) or `call:<name>` (a library call's argument); `bytes` is 0 when the length is computed at run time. Its outcome and reason:

| Outcome     | Reason            | Meaning                                                                                                                                                                                       |
| ----------- | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `guarded`   | `access`          | An inline check of the bytes the access touches.                                                                                                                                              |
|             | `range`           | A check of a range whose length is computed at run time.                                                                                                                                      |
|             | `string`          | A string argument, checked up to its terminator.                                                                                                                                              |
|             | `checked-call`    | The call goes through the runtime's checked version of the function.                                                                                                                          |
|             | `typed-unbounded` | An access of a safe function through a pointer whose bound the compiler does not know (loaded from a place no declaration bounds, or through `void *`), or a conversion of one (RFC 0042 §4). |
|             | `reference`       | A safe function's test of a reference it loaded from a field, which stops at a released heap block (RFC 0043 §7).                                                                             |
| `proven`    | `in-bounds`       | It lies inside a local or a global at an offset whose range is known (RFC 0035 §6.1).                                                                                                         |
|             | `dominated`       | A guard on the same pointer covers its bytes, with nothing between that may free (§6.2).                                                                                                      |
|             | `merged`          | It is merged into one guard of nearby accesses on the same pointer (§6.3).                                                                                                                    |
|             | `optimized`       | The optimizer removed every copy of the access.                                                                                                                                               |
|             | `typed`           | A safe function compares it with its pointer's bounds, those typed memory gives a loaded pointer included, or needs no check (RFC 0041 §4, RFC 0042 §4).                                      |
| `unguarded` | `unsafe`          | It lies in a `WEAVEC_UNSAFE` region or a function excluded from AddressSanitizer.                                                                                                             |

The rows are collected when the guards are inserted, before the optimizer; an access to a local or a global at a constant offset inside it gets neither a guard nor a row. A loop whose whole range was checked once still counts its accesses as `guarded`. `-fweavec-summary` prints the unit's counts:

```text
weavec: lookup.c: 3 accesses: 1 proven, 2 guarded, 0 unguarded
```

A unit with safe functions adds their count and its pointer fields': `…, 0 unguarded; 7 of 9 functions safe; 4 owner and 2 reference fields`. In a C++ unit the `functions` list names each function by its qualified name, and the `fields` list has each member of the unit's classes that owns (`owner`: an object with a destructor to run), refers (`reference`: a raw pointer), borrows (`borrowed`: a reference, a view, a `WEAVEC_BORROWED` pointer), shares (`shared`) or erases (`erased`); version 7 added the last two kinds (RFC 0044 §12).

In a Makefile, pass a directory so parallel compiles write separate files:

```sh
make CC=weavec-cc CFLAGS="-O2 -fweavec-ledger=build/ledger/"
```

Every ledger is written to a temporary file and renamed into place. A link writes no ledger.

## Removed options

RFC 0043 removed `-fweavec-typed` and `-fno-weavec-typed`: `-fweavec-safe` now means what `-fweavec-typed` meant, with ownership added, and there is one kind of safe function. The driver rejects the flag with `'-fweavec-typed' was removed: -fweavec-safe makes a unit safe, with typed memory and ownership (RFC 0043)`.

RFC 0036 deleted the advisory ownership and lifetime analysis, with no aliases. The `weavec` tool is gone with all of its options (`--whole-program`, `--dump-analysis`, `--dump-kinds`, `--budget=` and the rest), and so are these `weavec-cc` flags, each now an `unknown WeaveC flag` error: `-fweavec-diagnose` and `-fno-weavec-diagnose`, `-fweavec-budget=`, `-fweavec-unit-budget=`, `-fweavec-dump-analysis` and `-fweavec-analysis-stats=`. The diagnostic controls (`-Wweavec`, `-Wweavec-<id>`, `-Wno-weavec-<id>`, `-Werror=weavec[-<id>]`, `-Wno-error=weavec[-<id>]`) are no longer WeaveC's: they reach Clang, which warns that each is an unknown warning option (`-Wunknown-warning-option`, an error under `-Werror`). `weavec.h` keeps only `WEAVEC_UNSAFE`; a program that uses one of its other annotation macros no longer compiles until it stops using it.

RFC 0035 removed these, also with no aliases (each is an unknown-flag error): `-fno-weavec-runtime` and `-fweavec-runtime` (use `-fweavec-checks=none`); `-f[no-]weavec-stack-objects` and `-f[no-]weavec-global-objects`; `-fweavec-require=` and `WEAVEC_REQUIRE_SAFE` with the require levels; `-fweavec-link=`, `-fweavec-link-budget=` and the `<object>.weavec` unit records; `-fweavec-ledger-format=` (SARIF); and `-fweavec-print-prelude`. Earlier RFCs removed the checked-mode options of RFCs 0018–0029, `-fweavec-exclusive-borrows`, `-fweavec-strict`, `-fweavec-analysis-cache=`, `-fweavec-analyze-headers` and `-fweavec-report-unannotated`.
