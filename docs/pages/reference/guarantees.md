description: What a program compiled by weavec-cc is guaranteed at run time (accesses, bounds, releases, reuse only after a sweep, fortified and field sizes, poisoning, colors, returned frames), what safe functions add (typed memory and ownership), which memory the runtime tracks, the assumptions behind it, and what is and is not caught.

`weavec-cc` guards every memory access of the C and C++ code it compiles and removes a guard only where a simple local rule proves it redundant. The guarantee below is a property of the compiled program and its runtime. It is specified by [RFC 0037, _Soundness_](/rfcs/0037-complete-sweep-and-colors/#soundness), which keeps (A), (B) and (R) of [RFC 0035](/rfcs/0035-guard-by-default/#soundness) and (P) of [RFC 0036](/rfcs/0036-deterministic-heap-reuse/#soundness), completes (T) and (F), and adds (C) and (U), with the precondition and (A) amended by [RFC 0038](/rfcs/0038-drop-in-everywhere/#soundness), and extended to C++ by [RFC 0039](/rfcs/0039-cxx/#soundness), which adds (K); the RFCs' _Implementation amendments_ are authoritative, and this page restates them.

## The guarantee

For a program whose every unit is compiled by `weavec-cc` or `weavec-c++` in an enforcing mode (the default `-fweavec-checks=trap`, or `verify`; `report` only with `WEAVEC_RT_ABORT=1`), whose every image `weavec-cc` linked uses the process's one runtime, and whose allocator is the runtime's (the executable was linked by `weavec-cc`, or the runtime was preloaded), every memory access outside a `WEAVEC_UNSAFE` region satisfies the properties below. A guarded image in a process whose allocator is another's (a guarded library loaded by a program `weavec-cc` did not link, on Linux) keeps them for its frames and globals and for blocks the runtime allocated; the rest of the heap is untracked memory, and the runtime says so once.

- **(A) Accesses.** A load, store, atomic operation or memory intrinsic (`memcpy`, `memmove`, `memset`) of _w_ bytes at address _a_ executes only if every byte of [_a_, _a_ + _w_) is _addressable_ when it runs; otherwise the program traps before the access. The same holds for each memory argument of a call to a function in the [library table](https://github.com/weavefoundry/weavec/blob/main/lib/Core/LibrarySpec.txt), over the bytes the table says the call accesses, computed from the arguments, or, for a string, up to its terminator. For an argument a search reads (`strchr`, `strcspn`, `strspn`, `strpbrk`, `strstr`, `memchr` and their kin, marked `scan`), those are the bytes from the argument to where the call stopped, which its result says; they are checked when the call returns, before the result is used. A call that may throw (an `invoke`) is a call.
- **(B) Bounds.** An index `a[i]` into an array whose bound its type declares traps unless 0 ≤ `i` < _n_, or `i` ≤ _n_ where only the address is taken. A trailing array of a struct, which may be flexible, is excluded. In C++, an element access of a standard container that the C++ library's hardening checks (`operator[]`, `front`, `back`, a `span`'s, a `string_view`'s) is within the container, or the program traps (`library-assertion`).
- **(R) Releases.** A release through the runtime's allocator (`free`, `realloc` and the rest of the family, `operator delete` and `operator delete[]` in every form) releases null or the start of a live heap object allocated by the matching form (`malloc` and its kin for `free` and `realloc`, `new` for `delete`, `new[]` for `delete[]`), and a sized `delete` names the object's size; anything else stops the program. On Darwin, a release made by the system's own libraries is not checked against the form.
- **(K) Containers.** A byte of a `std::vector`'s or `std::deque`'s storage outside its elements is not addressable (`container-overflow`) while the code that changes the container's size keeps its annotations (A9).
- **(T) Temporal.** A byte of a released heap block is not addressable until a _sweep_ has found no pointer to the block in the threads' registers (vector registers too), stacks and thread-specific data, the process's readable memory but code and shared files it cannot write through, and the live heap. An access through a pointer the program held when the block was released therefore traps, however much it allocated since, and so does a second release of the block.
- **(F) Fortified and field sizes.** A fortified library call (`__strcpy_chk(d, s, 8)`, and the other `_chk` forms) writes no more than the size its `__builtin_object_size` argument states, and a string or formatting call (`strcpy`, `strcat`, `sprintf`, `snprintf` and their kin) into an array field of a struct, other than its last, writes no more than the field, or the program traps (`intra-object-overflow`).
- **(C) Colors.** Each tracked object (heap slot, local, global) carries one of 111 colors in the shadow. An access whose address the function computes from a pointer by arithmetic traps when its bytes lie in a tracked object of another color than the pointer's, unless the pointer points inside a live heap block other than at its start (a one-based array, a compressor's biased window base). Neighboring heap slots, any two heap slots fewer than 111 apart, the locals of one frame and globals registered fewer than 111 apart always differ; any other two objects share a color with probability 1 in 111 (1 in 7 when either byte is in an object's partial last granule).
- **(U) Returned frames.** An access to a local of a function compiled by WeaveC that has returned, or that an exception unwound, traps (`stack-use-after-return`) until another frame with tracked locals is laid over those bytes, or the access runs on another thread or stack.
- **(P) Poisoning.** A byte the program poisoned through AddressSanitizer's interface is not addressable until the program unpoisons it.

A function excluded from AddressSanitizer (`__attribute__((no_sanitize("address")))`, `no_sanitize_address`, `disable_sanitizer_instrumentation`) is treated as an unsafe region. Code inlined from an unsafe region stays unguarded wherever it lands.

## Safe functions

A function marked `WEAVEC_SAFE`, or defined in a unit compiled with `-fweavec-safe` ([RFC 0041](/rfcs/0041-safe-c/), [RFC 0042](/rfcs/0042-typed-memory/), [RFC 0043](/rfcs/0043-ownership/); [the guide](/guides/safe-c/)), compiles only if it keeps [Safe C's rules](/reference/rules/). It relies on **typed memory**: every pointer in memory that safe code reads through a declaration that bounds it (a struct field, a parameter, a result) is null or satisfies that bound, and every owner is the only one:

- **(W1) Single.** An unannotated `T *` points to the `sizeof(T)` bytes of one object.
- **(W2) Counted.** A `WEAVEC_COUNTED_BY(n)` or `WEAVEC_SIZED_BY(n)` pointer has the bytes its count gives, the count read where the annotation names it, in one object.
- **(W3) Terminated.** A `WEAVEC_NULL_TERMINATED` pointer has a zero byte at or after it, within its object or on the byte after a heap block.
- **(W4) Typed pointees.** The bytes (W1) and (W2) describe hold, where their type has a pointer, values that satisfy this too.
- **(W5) Owned.** A place declared `WEAVEC_OWNED` holds null or a pointer into a live heap block that no other owner holds.

"One object" is a live object, a released heap block not yet reused, or a local in its scope. Under the precondition of [the guarantee](#the-guarantee) and the assumptions below:

- **(S1) Bounds.** An access through a pointer whose bounds are known (a bounded parameter, a local, a global the unit defines, an allocation, a call whose result has a bound, a pointer loaded from a field whose declaration bounds it, and pointers computed from them) lies within those bounds, or the program traps (`pointer-out-of-bounds`): at a constant offset inside one object, inside a counted pointer's bounds by a comparison, at a string's current byte, which is at or before its terminator. An access through a pointer whose bound is unknown keeps its guard and (A).
- **(S4) Stack lifetime.** A local whose address may outlive its scope is allocated from the heap for the scope; a pointer parameter is stored or returned only when declared `WEAVEC_ESCAPES`, `WEAVEC_OWNED` or `lifetimebound`; an escaping or owned parameter does not point into the stack (`stack-escape`).
- **(S5) No forged pointers.** No pointer is made from an integer, from the bytes of another type, or from a union member that may hold another.
- **(M1) Typed memory is kept.** Every store, argument and result of a safe function into a place that declares a bound satisfies it, or a comparison stops the program (`bounds-conversion`, `unterminated-string`), or the function did not compile.
- **(M2) Accesses.** An access of a safe function lies inside its pointer's object, as (S1) says.
- **(M3) Heap lifetime.** A pointer to a released block reaches that block's bytes, which stay as the program left them, and no block a referenced released block refers to is reused either. (This restates RFC 0041's (S3).)
- **(M4) Entry.** A pointer that code which is not safe passes to a safe function, or returns to one, satisfies its declared bound when it arrives (a check against the shadow). (This restates RFC 0041's (S2).)

### Ownership

For a program that also meets O-A1 to O-A3:

- **(O1) One release.** Every release in a safe function consumes an owner: the function holds the owner, has not moved or released it on any path that reaches the call, and cannot use it afterwards. A safe function does not release a block it borrowed or loaded as a reference.
- **(O2) No use of what an owner no longer holds.** A safe function does not use an owner after moving or releasing it, and does not use a borrow after the owner it was taken from, or any owner above that one, was moved, released or replaced, by the function itself or by a call it made that could do so.
- **(O3) No owner dropped.** On every path, a safe function moves or releases each owner it names before the owner goes out of scope, is assigned over, or the function returns; or the owner is null there.
- **(O4) References are checked when loaded.** A pointer a safe function loads from a place that is not an owner is tested, before the function first accesses memory through it or passes it on, not to point into a released heap block (`heap-use-after-free`).
- **(O5) What is left.** A use after free in a safe function can then go only through a pointer that was live when a safe function loaded it as a reference (or received it from code that is not safe, or read it in place below a global owner) and whose block was released while that function, or one it called, still used it. (M3) confines it to the released block.

(O1) to (O3) are facts about the source: they hold in whatever build the program ships in, by whatever compiler, as long as the code that compiled is the code that is built. (O4), (M1) to (M4) and every spatial check need `weavec-cc`.

The ownership rules are not load-bearing at run time. No guard is removed and no block skips the quarantine on their strength: every released block waits for a sweep as in guarded code, so (T) and (M3) hold whether or not the rules are right, and a hole in a rule is a missed compile error, not a lost check. An owner the function does not name exactly (an element at an index, `*pp`) is not checked for the block an assignment over it may drop, nor is an array of owners when it is released, and a cycle of owners, a block whose owner is alive at `exit` and an owner held by code that is not safe are not reported.

### What gets weaker

A safe function's guarantee is conditional on T-A1 and O-A1; colors and redzones do not apply to its accesses (the comparisons replace both, and are exact inside an object); and a use after free through a pointer it loaded before the block was released is not reported, except through a reference when it is loaded (O4). `-fweavec-safe-checks=full` keeps every guard in safe functions, and `-fweavec-checks=verify` keeps each guard they dropped as a monitor that reports `weavec.proven` if it would have failed.

### Assumptions

They assume, beside A1–A9:

| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| **S-A2** | Code not built by `weavec-cc` keeps no pointer it was passed beyond the call unless the parameter is `WEAVEC_ESCAPES`.                                                                                                                                                                                                                                                                                                           |
| **S-A3** | No data race on a pointer and the count that bounds it.                                                                                                                                                                                                                                                                                                                                                                          |

| **T-A1** | Code that is not safe (guarded and unsafe functions, code WeaveC did not compile) keeps memory typed wherever safe code reads it, (W5) included: it stores a pointer where a declaration bounds it only when the pointer satisfies the bound, changes a count only with its pointer, writes no other bytes over a pointer, and stores in an owner only a block no other owner holds. `weavec-cc --weavec-audit` lists that code. |
| **T-A2** | A declaration marked `WEAVEC_SAFE` in a unit with safe functions names a function defined safe. A false one fails to link.                                                                                                                                                                                                                                                                                                       |
| **T-A3** | A pointer inside a released block the program can still reach meets A6: the sweep reads referenced released blocks.                                                                                                                                                                                                                                                                                                              |
| **T-A4** | No data race on a pointer safe code loads and a store that changes what it points to, nor on a pointer and its count (S-A3).                                                                                                                                                                                                                                                                                                     |

The audit marks the functions that are not safe and have an owned parameter or result (`owns`).  |
| **O-A2** | The arguments with which code that is not safe calls a safe function do not overlap in the way rule `call-alias` forbids.                                                                                                                                                                                                                                                                                                        |

Guarded functions keep (A)–(P) unchanged. A guard a safe function drops is justified by its bounds, or by typed memory, which each safe function keeps by rules checked inside it and which holds only if every writer keeps it: the one removal that is not local to a function, and `-fweavec-checks=verify` monitors it like the others.

## Safe C++ functions

A C++ function made safe by `weavec-c++ -fweavec-safe` or `WEAVEC_SAFE` ([RFC 0044](/rfcs/0044-safe-cxx/), [the guide](/guides/safe-cxx/)) is checked when it compiles and is compiled as a guarded function: (A) to (P) hold for it unchanged, and nothing at run time rests on the rules. For a program that meets X-A1 to X-A5, in every build:

- **(X1) No raw owner.** A safe function allocates and releases heap memory only through objects whose destructors release it: it contains no `new`, no `delete`, and no call that returns or takes a raw owner.
- **(X2) No use of a moved object.** It does not use an object after moving from it, on any path, until it assigns to it.
- **(X3) No stale borrow.** It does not use a borrow or a view after an owner it points into was destroyed, moved, assigned, or passed to anything that could change what it owns, by the function itself or by a call it made. That includes the end of a local's scope and of the statement that made a temporary.
- **(X4) No borrow where the rules cannot follow it.** It does not return a borrow or a view of its own locals, and does not store one in memory that is not a view's.
- **(X5) No forged pointer.** It does no pointer arithmetic, indexes no raw pointer, and makes no pointer by a cast from an integer or from a pointer to an unrelated type.
- **(X6) What is left.** A temporal error in a safe C++ function can then go only through a reference (a raw pointer kept in a member or an element), through an object shared by `std::shared_ptr` that another holder changed, through a global, through a callable that captured `this` or an object a parameter refers to and is kept by an object that outlives it, through a callable that code which is not safe kept, or through an element moved out of a container; a spatial error can only be an index or an iterator out of range. All of them stop when they run, by (T), (A) and the library's checks.

(X1) to (X5) are facts about the source and hold under any compiler. They assume:

|          | Assumption |
| -------- | ---------- |
| **X-A1** | Code that is not safe (guarded and unsafe functions, system headers, code WeaveC did not compile) honors the declarations safe code sees: a `const` member function or parameter changes nothing an object owns, and a result that is a view points into the arguments the caller is told it may, or into something that outlives them. |
| **X-A2** | The arguments with which code that is not safe calls a safe function do not overlap in the way `call-alias` forbids, and a view it passes outlives the call. |
| **X-A3** | No other thread, and no signal handler, destroys, moves or changes an owner while a safe function uses it or a borrow into it. |
| **X-A4** | The standard library behaves as the standard specifies: a `const` member function invalidates nothing, a member function with a `const` overload of the same parameters only gives access, its own functions accept the arguments their specification allows, and the types Clang marks as owners and pointers are. |
| **X-A5** | A moved-from object of a library type may be assigned and destroyed. |

The audit lists what the rules do not follow: the functions and classes that are not safe, the reference, shared and erased members.

## What is addressable

A byte is addressable unless the runtime knows it is not:

| Bytes                                               | Not addressable                                                                                                               |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| A heap object's slot in the runtime's allocator     | the bytes after the object's requested size; the whole slot once the object is released, until a sweep finds no pointer to it |
| A tracked local (in its function's frame)           | its redzones, always; the local before its scope begins and after it ends, and after its function returns                     |
| An `alloca` block or a variable-length array        | its redzone                                                                                                                   |
| A global the unit defines (a _tracked_ global)      | its redzone                                                                                                                   |
| Bytes the program poisoned through ASan's interface | until the program unpoisons them                                                                                              |
| A `std::vector`'s or `std::deque`'s storage         | the bytes past its elements (a granule a deque's front splits stays addressable)                                              |
| Low memory                                          | the lowest 64 KiB                                                                                                             |

Every other byte is addressable: memory the runtime does not track (other allocators, `mmap`, string literals, locals no guard can reach, frames and globals of code built without WeaveC), and the bytes of live tracked objects.

The runtime keeps one _shadow_ byte for every 16 bytes, saying how many of them are addressable and in what color of object, or why none are. Its allocator puts every object in a slot of the smallest size class strictly larger than the object, so at least one byte after every heap object belongs to no object. A released block joins a _quarantine_ and is never reused from there: only a sweep, which stops the program's threads and scans its memory conservatively for pointers, moves the blocks it found no pointer to back to the free lists.

The locals a guard can reach (the _tracked_ locals: an access to them is guarded, or their address escapes) are laid out in one frame with a 64-byte redzone before the first and at least 32 bytes after each; in a frame that would be larger than 512 bytes, locals whose lifetimes never overlap (the arms of a `switch`) may share bytes, as Clang's own frames share them. Each `alloca` block and variable-length array gets a redzone after it. Each tracked global gets a redzone after it and a 32-byte alignment.

## What is caught

- **Heap overflow** that touches a byte past the block (`heap-buffer-overflow`), with a paragraph that places the address relative to the block and gives the stack that allocated it. An access that jumps over the slot's tail into another live block lands on that block's bytes and passes.
- **Heap use after free and double free.** An access to a released block through any pointer the program still holds traps (`heap-use-after-free`), however much it allocated since, because the block is not reused while a pointer to it exists. The report gives the stacks that released and allocated the block. A safe function stops at the load of a reference to a released block (O4), and does not compile a use of an owner it released (O2). A second `free` or a `realloc` of a released block (`double-free`) and a `free` of an interior, stack or global pointer (`invalid-free`) stop the program at the call, in every check mode. The allocator validates every release in the image, from WeaveC's code or any other.
- **Stack and global overflow** into a redzone: an access that leaves a tracked local (`stack-buffer-overflow`), an `alloca` block or a variable-length array (`dynamic-stack-buffer-overflow`), or a tracked global (`global-buffer-overflow`) and touches its redzone. The report names the local and its function, or the global and its definition.
- **Use after scope.** An access to a local after its block has ended traps (`stack-use-after-scope`), at every optimization level, unless it lands in bytes that a local whose scope began later now shares (only in a frame larger than 512 bytes).
- **Overflow inside an object**, by an index into a declared array (B): `s.buf[i]` with `i` past `buf`'s declared bound traps (`index-out-of-bounds`) even when the bytes it would touch belong to the next field; and by a fortified string or `printf`-family call into a field (F): `strcpy(u->name, s)` into an 8-byte field traps (`intra-object-overflow`) where the C library's headers pass the field's size, as Darwin's do. glibc's headers fortify through inline functions, inside which Clang knows only the rest of the object, so on glibc such a call is checked against the end of the object, not of the field.
- **Faults the shadow did not see** (a wild address, the inaccessible middle of a huge block) print `weavec: memory-fault at pc …` and the stack of the faulting instruction before the program dies of the signal.
- **Null dereference.** An access at a small offset from null faults on the null page, or traps on the shadow of the lowest 64 KiB; one at a variable or large offset from a pointer not known to be non-null tests the pointer first (`null-dereference`).
- **Jumps into a neighbor** (C): an index or pointer computed from one heap block, local or global that lands in a live object of another color (`heap-buffer-overflow`, `stack-buffer-overflow`, `global-buffer-overflow`, with a line naming the base it was computed from before the paragraph of the object it landed in), including a loop whose versioned range starts in the neighbor.
- **Use after return** (U): `stack-use-after-return`, with a line saying the frame returned, a frame an exception unwound included. After an exception the live frames keep their redzones and scopes.
- **C++.** A use after `delete`, an iterator or pointer kept across a container's reallocation, a dangling `string_view` and a `unique_ptr`'s or `shared_ptr`'s object used after its release, as heap or scope errors; a release by the wrong form or a sized `delete` of the wrong size (`alloc-release-mismatch`: `operator delete of 0x…: allocated by operator new[]`); a read or write past a container's elements within its capacity (`container-overflow`, K); an index the C++ library's hardening rejects (`library-assertion`); and the buffer arguments of `std::string`'s and the streams' members the C++ library defines in its shared object (`append`, `assign`, `insert`, `replace`, the `find` family, `compare`, `ostream::write`, `istream::read`, `get`, `getline`).
- **Library calls.** A call in the library table whose memory arguments would be read or written outside their objects traps before the call: `memcpy(dst, src, n)` with `n` past either object, a `%s` argument of a `printf`-family call with a literal format that has no terminator in its object (`unterminated-string`), fortified forms (`__builtin___memcpy_chk`) as their plain forms. `strcpy`, `stpcpy`, `strcat`, `sprintf`, `vsprintf`, `snprintf` and `vsnprintf` go through the runtime's checked versions, which compute what the call writes before it writes and check the `printf`-family `%s` and `%n` arguments, through a `va_list` too; `gets` through one that checks each byte before it writes it; `strcmp`, `strncmp`, `strcasecmp` and `strncasecmp` through versions that check the bytes the call read up to where it stopped; the searches (`strchr`, `index`, `strchrnul`, `strcspn`, `strspn`, `strpbrk`, `strstr`, `strcasestr`, `memchr`, `rawmemchr` and the wide ones) after the call, over the bytes up to where they stopped, so a search inside an unterminated buffer that stops at a match there runs clean; the `scanf` family through versions that check, after the call, what each conversion that ran wrote; the `strto*` and `ato*` number parsers through versions that check the bytes the parse read; `readv`, `writev`, `preadv`, `pwritev`, `recvmsg` and `sendmsg` through versions that check every buffer their vectors name; `stat`, `lstat`, `fstat`, `fstatat`, `gmtime_r`, `localtime_r`, `uname`, `inet_pton`, `inet_ntop`, `if_indextoname` (and Darwin's `sysctl`, `sysctlbyname`, `basename_r`, `dirname_r`) through versions that know the C types' sizes; `getline` and `getdelim` against the capacity they are given; `accept`, `getsockname`, `getpeername`, `getsockopt` and `recvfrom` against the lengths they are passed; the `printf` family (`printf`, `fprintf`, `dprintf`, `asprintf`, their `v` forms, Darwin's `sprintf_l` and `snprintf_l`) through versions that read the format, constant or not; wide strings through the runtime's scan; and a library function called through a pointer, whose address is replaced by that of a guarded thunk. Overlapping operands of `memcpy` and of the other calls whose table row says they must not overlap trap as `overlapping-copy`.
- **Poisoned memory.** Bytes a program poisons through AddressSanitizer's interface (`ASAN_POISON_MEMORY_REGION`, as a pool allocator does for its free space) trap when a guarded access reaches them (`use-after-poison`). A program that sends its objects to `malloc` when it sees `__SANITIZE_ADDRESS__` (QuickJS does) gets its objects tracked one by one.

The runtime's allocator also serves the C library's own allocations (`strdup`, `getline`, `asprintf`), so their blocks are tracked too.

## What is not caught

- **Some jumps over a redzone.** A jump into an object of the same color (1 in 111 for objects that are not neighbors; an attacker who knows the layout can choose one), a jump from a pointer into the middle of a heap block, a pointer moved into another object by one function and used in another (it is checked against the object it points into), and an access at a constant offset that its guard already covers.
- **Some uses after return.** Through a frame a later call at the same depth laid a tracked frame over, through another thread, on a stack that is not the thread's own, and through a local of a frame `longjmp` abandoned (the jump clears the stack's shadow).
- **A pointer jump inside one object by arithmetic.** A cursor walked from one field of a struct into the next stays inside its object; only indexes into declared arrays (B) and fortified calls (F) are checked against a field.
- **Hidden pointers.** A pointer the program stores only in a form the sweep does not recognize (XOR-linked, transformed, written to a file, held only by the kernel) does not keep its block from reuse (A6); a use of the block through it after a sweep reuses the block is not caught.
- **The program's own poisoning of a local or a global at a constant offset.** An access to a local or a global at a constant offset inside it needs no guard, so it is not checked against bytes the program poisoned there; accesses at a computed offset are.
- **Untracked memory.** Memory from another allocator (unless the program poisons it through ASan's interface), `mmap`, string literals, and objects of code built without WeaveC have no redzones; an access into them passes (A1). A write into a string literal passes its guard (the hardware usually faults on it). `WEAVEC_RT_STATS=1` prints, at exit, how many MiB of writable memory the runtime does not track.
- **Functions outside the library table** are not checked at the call, nor is a library function found with `dlsym`, nor a library's own use of a buffer the program freed (`setvbuf`); their own accesses are guarded only if `weavec-cc` built them (A2).
- **`memcpy` and `memset` past a field** inside its struct: code that copies over consecutive fields on purpose is common and correct in practice.
- **Uninitialized pointers** in memory other than locals and the runtime's heap (which are zero) point anywhere; accesses through them are guarded, and one into untracked memory passes.
- **Data races.** A release by another thread between a guard and its access is not caught (A3).
- **Anything in a `WEAVEC_UNSAFE` region** or an AddressSanitizer-excluded function, and **any code not compiled by `weavec-cc`**: other compilers, precompiled libraries (the C++ library's shared object among them: its `std::string` and stream members that take a buffer are checked at their calls, its other internals and virtual calls into it are not; `basic_string::copy` is checked at its first byte), Objective-C sources.
- **C++ containers' internals other than their size.** A `std::string`'s inline buffer and a `std::map`'s nodes are checked as the objects they are, not against the container's logical extent; a container whose storage is not the runtime's heap is untracked memory; a class-specific `operator new` that carves objects out of larger blocks shares the block's shadow, as a C pool does.
- **Leaks** outside safe functions (a safe function that drops an owner it names does not compile, (O3)), integer overflow as such, type confusion within an object, and inline assembly. Outside safe functions WeaveC reports nothing before the program runs; a static analyzer (such as the Clang static analyzer) finds leaks.

## Assumptions

|        | Assumption                                                                                                                                                                                                                                                                                                                                                   |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A1** | An access to bytes the runtime does not track (memory from another allocator that the program does not poison through ASan's interface, `mmap`, string literals, code built without WeaveC) is to a live object it stays inside.                                                                                                                             |
| **A2** | A function in the library table accesses only what its row says. A function outside it is not checked at the call. A search on a string with no terminator in its object that never stops reads past the object, as the C library does, before the check after the call reports it (or faults).                                                              |
| **A3** | No other thread releases memory between a guard and its access: the guard and the access are not atomic together.                                                                                                                                                                                                                                            |
| **A4** | The program does not write the runtime's shadow or metadata except through guarded accesses.                                                                                                                                                                                                                                                                 |
| **A5** | A frame left by `longjmp`, `pthread_exit` or another call that does not return leaves no poison behind: the stack's shadow below the caller is cleared before the call. A frame left by an exception is marked returned when the exception is caught or reaches a cleanup in guarded code.                                                                   |
| **A6** | A pointer to a heap block is kept, while the program may still use it, as a whole aligned pointer in memory the sweep scans (any readable mapping but code and shared files the program cannot write through) or in a register. One kept only in memory the program made inaccessible, in device memory or as a transformed integer does not keep its block. |
| **A7** | On Linux every thread accepts the sweep's signal within a second (`pthread_sigmask` and `sigprocmask` never block it). A thread that blocks it by other means holds up the reuse of released memory (nothing is reused until it accepts), never safety.                                                                                                      |
| **A8** | A pointer the function did not compute (a parameter, a loaded value, a call's result) points into the object it is meant to: (C) checks arithmetic from it, not the pointer itself.                                                                                                                                                                          |
| **A9** | Every unit that instantiates a standard container and changes its size is compiled with the same container annotations (`weavec-c++`, or ASan); `WEAVEC_RT_CONTAINERS=0` turns (K) off for a program that links one that is not.                                                                                                                             |

Outside safe functions, no guard is removed because of what another function does, so nothing is assumed about callers, callees or the rest of the heap. The rules that remove guards are local to a function (an access inside a local or global at a known offset, an access a dominating guard on the same pointer covered with nothing between that may free, guards merged in a block, a loop whose whole range was found addressable before it ran), and `-fweavec-checks=verify` monitors them: it keeps every removed guard as a monitor that reports `weavec.proven` if it would have failed.

## False traps

A correct program does not trap. A program that breaks C's rules in a way that usually works does, as it does under AddressSanitizer:

- reading a word at a time past the end of a string or a buffer (a fast `strlen`, a hash over a key's last word);
- using a block's tail beyond its requested size (`malloc_usable_size` returns the requested size);
- indexing a multidimensional array past an inner bound (`int m[4][4]; m[0][k]` with `k` ≥ 4), which (B) checks;
- in C++, releasing `new[]` memory with `delete` (or `new` memory with `free`) where the types are trivially destructible, reading `v[v.size()]` without using the value, and a container grown by code built without its annotations (A9).

`weavec-cc` compiles C as AddressSanitizer would (`__SANITIZE_ADDRESS__` is defined and `__has_feature(address_sanitizer)` is true), so code that keeps such reads from ASan behind those tests, or in a function marked `no_sanitize("address")`, needs no change. Other code needs a fix or a `WEAVEC_UNSAFE` region. A program that depends on the system allocator's identity (a `malloc_zone_t` of its own, allocator introspection, `mallopt`) sees WeaveC's allocator instead.

## Without the runtime

Nothing is enforced without the runtime. `weavec-cc` builds without it, and compiles without guards and without array-index checks, under `-fweavec-checks=none`, `-ffreestanding`, `-nostdlib` and its kin, a sanitizer that replaces the allocator (`-fsanitize=address` and the like), and on targets other than 64-bit Darwin and Linux; the link says so. A program that defines `malloc` itself keeps its allocator: its guards stay, but its heap is untracked, guards pass on it and releases are not validated. See [the runtime](/reference/cli/#the-runtime).
