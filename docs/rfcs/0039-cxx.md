# RFC 0039: C++

- **Status**: Accepted
- **Authors**: WeaveC authors
- **Created**: 2026-11-06
- **Tracking issue**: TBD
- **Supersedes / superseded by**: Amends RFC 0035 §1 (WeaveC guards C
  only) and its assumption A5 for frames unwound by an exception; RFC
  0035 §3's clearing of the stack before every call that does not return,
  for the calls that unwind; RFC 0036 §5's ASan contract, whose container
  annotations become checks; the library table's grammar (RFC 0035 §2.5,
  RFC 0036 §6, RFC 0038 §2); the enforcement ledger's format (RFC 0035
  §9, version 3 to 4); AGENTS.md rule 9's runtime line budget. RFC 0038's
  other sections stay.

This RFC was drafted before implementation. On 2026-11-06 the project
owner accepted the recommendation of a milestone assessment of v0.19.0:
guard C++ as WeaveC guards C, in one large change, with breaking changes
and no compatibility layers. Tracking the objects of programs' own
allocators (pymalloc, palloc, pools), exact spatial checks, deterministic
use after return and Windows were considered and are not taken
(*Alternatives*). Finishing RFC 0038 (the release runners, linux-x86_64,
the weekly corpus run) is a prerequisite done under RFC 0038, not here.

## Summary

WeaveC guards C. Every C++ source a build hands it is compiled as Clang
compiles it, without guards, frames, colors or array-bound checks, and
links with the guarded C. A project with any C++ in it (its library, its
tests, its tools) is therefore outside the guarantee, whose precondition
is that every unit is compiled by `weavec-cc`. The roadmap names C++ the
next milestone; RFC 0038 gave it a runtime that every image of a process
shares.

Measured on v0.19.0, the guard passes already work on C++ almost
unchanged: with the one line that skips C++ removed, a program built from
the C++ standard library's containers, strings, regular expressions,
streams, exceptions and threads runs as it does under Clang in 0.7 times
ASan's CPU time, and six of ten C++ bug probes stop (ASan stops six, a
different six). What does not work is
specific to C++: library calls in a scope that owns an object with a
destructor are not guarded, an exception wipes the shadow of the whole
stack, `new` and `delete` are not told apart from `malloc` and `free`, the
standard library's containers and its bounds checks are not wired to the
runtime, and the parts of `std::string` that live in the C++ library's
shared object are unchecked.

This RFC:

1. **Guards C++** (§1): `weavec-c++` is the C++ driver (`CXX=weavec-c++`),
   C++ units get the guards, frames, globals, colors, array-bound checks
   and zero-initialized locals C units get, and links add the C++
   standard library as Clang's driver does.
2. **Guards calls that can unwind** (§2): every pass treats an `invoke` as
   the call it is, so a library call inside a scope with a destructor is
   guarded, and a check after a call is placed on its normal path.
3. **Keeps the stack's poison across exceptions** (§3): only the frames an
   exception unwinds are marked returned; the live frames keep their
   redzones and scopes, where today every throw and every `_Unwind_Resume`
   clears the whole stack and turns off color checks on it for the rest of
   the run.
4. **Checks `new` and `delete`** (§4): the runtime defines the replaceable
   allocation functions, records which form allocated each block, and
   stops a release by the wrong form or by a sized `delete` of the wrong
   size.
5. **Checks containers** (§5): the runtime implements ASan's container
   annotations, so the bytes of a `std::vector`'s or `std::deque`'s
   storage past its size are not addressable (`container-overflow`).
6. **Turns on the standard library's bounds checks** (§6): C++ compiles
   define libc++'s fast hardening mode and libstdc++'s assertions, as C
   compiles get `_FORTIFY_SOURCE`, and a failed check is a WeaveC report
   (`library-assertion`) instead of a silent trap.
7. **Guards the C++ library's buffer members** (§7): rows of the library
   table for the members of `std::string` and the streams that the headers
   leave to the library's shared object and that take a raw buffer.
8. **Measures C++** (§9): C++ projects in the corpus, C++ programs in the
   programs tier, a sealed C++ set, C++ detection probes and benchmarks.

C units compile and run as with v0.19.0, within 2%.

## Motivation

Measured on main at `d6af0f51` (v0.19.0) on darwin-arm64 (Apple M3, `dev`
preset, the SDK's libc++ 22), with the reference `clang++` 23.1 and ASan
(`-fsanitize=address`). The prototype is v0.19.0 with the C++ exclusion in
`runCc1Job` (`lib/Frontend/Driver.cpp`) skipped; its diff and the probes
are kept in the evaluation directory of the assessment.

### C++ is not guarded

`runCc1Job` returns to Clang for any unit whose language is C++,
Objective-C, OpenCL or CUDA, and the compatibility reference says so. A
read four elements past `new int[4]` and past a `std::vector<int>(4)`'s
data both pass silently when the file is built with `clang++` beside
WeaveC's C, and `weavec-cc file.cpp` does not link (the C driver adds no
C++ standard library: `operator new` is undefined). The guarantee's
precondition excludes every program with a C++ unit, and many C projects
have one: their tests (googletest), a binding (flac's libFLAC++), a tool.

### The passes already work on C++

With the exclusion skipped and `--driver-mode=g++`:

| Probe | Prototype | ASan |
| --- | --- | --- |
| A program over `vector`, `string`, `map`, `unordered_map`, `deque`, `list`, `regex`, `ostringstream`, `format`, `shared_ptr`, `variant`, `any`, exceptions thrown through 10 frames, 4 threads, `async`, `fstream`, `filesystem` (20 rounds) | same output as `clang++`, no report | same output |
| Its `-O2` user CPU (best of three) | 0.48 s (reference 0.19 s: 2.5×) | 0.68 s (3.6×) |
| Its `-O2` compile | 2.68 s (reference 1.62 s: 1.65×) | 2.22 s |
| Use after `delete`; a pointer kept across a `vector` reallocation; a `string_view` of a returned long `string`; one of a returned short `string`; `vector(4)[4]`; a `unique_ptr`'s object used after `reset` | all six stop (the short string as `stack-use-after-scope`) | five stop (not the short string; ASan's use after return is off on Darwin) |
| `v.reserve(8); v.push_back(1); v[5]` | passes | `container-overflow` |
| `new S[2]` released by `delete` | passes | passes (off on Darwin by default) |

The guards, the frames, colors, the sweep and the shared runtime need no
change to run C++. Five gaps are specific to C++.

### A call in a scope with a destructor is not guarded

In C++ a call that may throw, made while an object with a destructor is
alive or inside `try`, is an `invoke`. `guardLibraryCalls`, the thunks of
library functions whose address is taken and the wrappers' redirection
(`lib/Frontend/GuardLibrary.cpp`) collect `CallInst`s only:

```cpp
std::string keep(40, 'k');           // a destructor in scope
char *buf = (char *)malloc(8);
read(fd, buf, 64);                   // passes in C++; the C form stops
```

Darwin's headers do not declare the C library `noexcept`, so a call in
such a scope to a C library function Clang does not know as a builtin
(`read`, `recv`, `getline` and the like) is an `invoke`. The rules that remove guards
already look at every `CallBase`.

### An exception wipes the stack's shadow

`unpoisonBeforeNoReturn` (`lib/Frontend/GuardFrames.cpp`) calls
`__weavec_rt_unpoison_stack` before every call that does not return,
`__cxa_throw` and `_Unwind_Resume` included. It clears the shadow from the
caller to the top of the stack, the live frames' redzones and scopes with
it, and sets `stackLostColors`, a process-wide flag that turns off color
checks on every thread's stack for the rest of the run
(`runtime/weavec_guard.c`). That is right for `longjmp`, whose target is
unknown at the call. For an exception the unwinder knows exactly which
frames die:

```cpp
int main(int argc, char **argv) {
  char buf[16];
  try { risky(1); } catch (const std::exception &) {}   // any throw
  fill(buf, 40);                     // stops without the throw; passes after it
}
```

Built with ASan the same program behaves the same way: its interceptor of
`__cxa_throw` unpoisons the whole stack too. C++ code that throws routinely
(parsers, I/O, `std::stoi`) loses stack checks at its first exception, and
every function with a destructor calls `_Unwind_Resume` on its way out of
one.

### `new` and `delete` are `malloc` and `free`

The C++ library's `operator new` calls `malloc`, so its blocks are tracked
and released blocks wait for a sweep. But the runtime cannot tell a block
from `new[]` from one from `new` or `malloc`: a release by the wrong form,
undefined behavior that corrupts the heap with most allocators (an array
cookie, a destructor loop over the wrong count), passes, and so does a
sized `delete` of the wrong size (a `delete` through a base without a
virtual destructor).

### The standard library's own checks are dark

- **Container annotations.** libc++'s `vector` and `deque` (and
  libstdc++'s `vector` under `_GLIBCXX_SANITIZE_VECTOR`) tell ASan which
  part of their storage holds elements. WeaveC compiles as ASan would
  (RFC 0036 §5), so libc++'s headers call the annotations, but
  `__sanitizer_annotate_contiguous_container` is an empty stub in
  `runtime/weavec_asan.c`, and the double-ended form `deque` calls is
  missing: a program that uses a `deque` (or a `regex`, which uses one)
  fails to link under the default flags. The prototype needed
  `-fno-weavec-asan-compat`.
- **Hardening.** libc++'s fast hardening mode checks `vector::operator[]`,
  `front`, `back`, `span`, `string_view` and `optional` accesses;
  libstdc++'s `_GLIBCXX_ASSERTIONS` checks the same. Neither is on by
  default. Turned on by hand, `v[5]` on a one-element vector stops, but as
  a bare `SIGTRAP` with no report. The message is in the binary: the trap
  carries a debug location in an artificial function named
  `__clang_trap_msg$libc++$…vector[] index out of bounds`, present under
  the location-only debug information WeaveC already turns on.

### The C++ library's shared object is unguarded

libc++ instantiates most out-of-line members of `basic_string<char>` and
`<wchar_t>` in its shared object (`extern template`), and libstdc++ does
the same. A call to them from guarded code is a call to a function outside
the library table: `s.append(buf, 64)` with an 8-byte `buf` passes with
WeaveC and with ASan, while `std::string(buf, 40)`, inline in the headers,
stops. The same holds for `ostream::write`, `istream::read` and
`getline(char *, n)`. libc++ 22 has no switch that makes the headers
instantiate those members.

### What is not the problem

Allocation volume, threads, RTTI, `thread_local`, coroutines (frames come
from `operator new`), multiple inheritance (base adjustments stay inside
one object, so one color) and lambdas needed nothing in the prototype. The
SDK's libc++ headers come from the platform, so a self-contained toolchain
needs no C++ library of its own.

## Soundness

### The guarantee

RFC 0037's guarantee, as amended by RFC 0038, is extended to C++:

- **Precondition.** Every unit of the program is compiled by `weavec-cc`
  or `weavec-c++` in an enforcing mode, and RFC 0038's conditions on the
  runtime and the allocator hold. The C++ standard library's shared object
  is code `weavec-cc` did not compile, as the C library is: its own
  accesses are covered by A2 and the rows of §7.
- **(A) Accesses** holds for C++ units as for C units, for every call,
  `invoke` included (§2).
- **(B) Bounds** gains: an element access of a standard container that the
  C++ library's hardening checks (§6) is within the container, or the
  program traps.
- **(K) Containers** (new): a byte of a `std::vector`'s or `std::deque`'s
  storage outside its elements is not addressable while the container's
  own code keeps its annotations (§5).
- **(R) Releases** gains: a release by `operator delete` or `operator
  delete[]` releases null or the start of a live block allocated by the
  matching form (`new`, `new[]`, or `malloc` for `free`), and a sized
  release names the block's requested size, or the program stops (§4).
- **(U) Use after return** gains: a frame an exception unwound is a frame
  that returned (§3).

### Assumptions

RFC 0035's A1–A4, RFC 0036's A6–A7 and RFC 0037's A8 stay. A2 covers the
C++ library's shared object; its members outside §7's rows access only
memory their object owns. A5 changes:

- **A5.** A frame left by `longjmp`, `pthread_exit` or another call that
  does not return leaves no poison behind: the stack's shadow below the
  caller is cleared before the call. A frame left by an exception is
  marked returned when the exception is caught or reaches a cleanup in
  guarded code (§3).

One is added:

- **A9.** Every unit that instantiates a standard container and changes
  its size is compiled with the same container annotations (`weavec-c++`,
  or ASan): a container grown by code built without them keeps a stale
  annotation. This is the precondition applied to templates;
  `WEAVEC_RT_CONTAINERS=0` turns (K) off for a program that links such a
  unit.

### Where this is more sound than v0.19.0

- C++ units are guarded at all.
- A library call made inside a C++ scope with a destructor is guarded.
- After an exception, the live frames keep their redzones and scopes, and
  color checks stay on for the stack; a pointer into an unwound frame
  traps as `stack-use-after-return` until the stack is reused. C frames
  unwound by an exception (C built with `-fexceptions` between C++ frames)
  get the same.
- `stackLostColors` becomes per-thread: one thread's `longjmp` no longer
  turns off color checks on every other thread's stack.

### Where this is less sound than v0.19.0

Nothing that v0.19.0 checks is checked less.

### Bugs deliberately not caught

As RFC 0038, plus:

- **The C++ library's internals.** A member of the C++ library's shared
  object not in §7 (a stream buffer's virtual `xsputn`, locale facets) and
  a virtual call into it are not checked at the call. `basic_string::copy`
  is checked at its first byte only: the bytes it writes depend on the
  string's size, which no argument names.
- **Containers from other allocators.** A container whose allocator is not
  `std::allocator` and whose storage is not the runtime's heap is
  annotated as ASan annotates it, but
  bytes outside the runtime's heap are untracked memory (A1).
- **Class-specific `operator new`** and allocators that carve objects out
  of larger blocks: their objects share the block's shadow, as C pools do.
- **Objective-C and Objective-C++** stay Clang's (*Future work*).
- **Container internals other than size.** `std::string`'s short-string
  buffer, `std::map`'s nodes and the like are checked as the objects they
  are, not against the container's logical extent: libc++ annotates only
  `vector` and `deque` for a library not itself built with ASan.

### Accepted false traps

- **A9's mixed builds**: a vector instantiated and grown by code built
  without the annotations traps as `container-overflow` when guarded code
  later reads an element the other code added. ASan has the same
  limitation and the same switch.
- **`new[]` released by `delete`** and the like stop, also where the types
  are trivially destructible and the C++ library's allocator would not
  notice: it is undefined behavior, and ASan reports it on Linux.

No other new false trap is expected; the corpus gate (G3) keeps none
accepted.

### Cost

C units change only by the runtime's allocation-kind bits (§4); expected
within 2% of v0.19.0. C++ units pay what C units pay, more because C++
code is call-dense and its inlined library code is guarded, plus
hardening's checks (libc++ documents the fast mode as meant for
production use, at minimal cost). Expected, from the prototype: C++
benchmarks at most 2.5 times the reference and below ASan; C++ builds at
most 2 times the reference's compile CPU.

## Detailed design

### 1. The C++ driver

**`weavec-c++`.** `weavec-cc` selects Clang's driver mode from its program
name, as `clang` does: invoked as `weavec-c++` (a link to `weavec-cc`) it
is in `g++` mode (`clang++`), so `.c` sources compile as C++, and links add
the C++ standard library (`-lc++` on Darwin, `-lstdc++` on Linux) and the
runtime. `weavec-cc --driver-mode=g++` is the same. `weavec-cc file.cpp`
behaves as `clang file.cpp` does (compiles C++, links without the C++
library). The release layout gains `bin/weavec-c++`; CMake projects use
`-DCMAKE_CXX_COMPILER=weavec-c++`, Make and Autoconf `CXX=weavec-c++`.
`--version` prints the same trailer.

**C++ units are guarded.** `runCc1Job` gives a C++ unit everything a C unit
gets: `configureEnforcement`, the ASan contract, unsafe regions and the
ledger. Objective-C, Objective-C++, OpenCL and CUDA units stay Clang's.
`-std=`, `-stdlib=`, modules, precompiled headers and header units keep
their meaning (RFC 0038 amendment 27 already gives C++ jobs Clang's actions).

**Hardening.** A C++ compile in an enforcing mode adds
`-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST` and
`-D_GLIBCXX_ASSERTIONS` (each library ignores the other's macro) unless the
command line defines or undefines `_LIBCPP_HARDENING_MODE`,
`_GLIBCXX_ASSERTIONS` or `_GLIBCXX_DEBUG`, as `_FORTIFY_SOURCE` is added
today (`wantsFortification` becomes `wantsLibraryChecks`).

**The standard library.** The C++ library and its headers are the
platform's: on Darwin the SDK's libc++, on Linux the distribution's
libstdc++ (or libc++ with `-stdlib=libc++`). The toolchain ships neither;
the installation guide adds `g++` (for libstdc++'s headers) to the Linux
requirements.

### 2. Calls that can unwind

Every pass that handles calls handles `llvm::CallBase`: an `invoke` is a
call whose normal path continues in another block.

- `guardLibraryCalls` collects calls and invokes; the guards before a call
  go before the `invoke`.
- A `scan` argument's guard (RFC 0038 §2) and any other check after a call
  go at the start of the `invoke`'s normal destination; when that block
  has other predecessors, the edge is split first. A check never goes on
  the unwind path.
- Wrappers (`wrapper(…)`) and the thunks of library functions whose
  address is taken replace the callee of an `invoke` as of a call; the
  runtime's wrappers do not throw, so an `invoke` of a wrapper is left as
  an `invoke` (the unwind edge is dead but harmless).
- `canLayOut` and the frames' exits already see `resume`; `GuardLoops`
  collects markers, which are always calls.

`test/Guards/cxx-invoke.cpp` pins the IR of each.

### 3. Exceptions

**The library table says which calls unwind and which end the process.**
Two clauses join the grammar:

```
clause ::= ... | 'exits' | 'unwinds'
```

`exits` marks a call that ends the process (`abort`, `exit`, `_exit`,
`_Exit`, `quick_exit`, `__assert_fail`, `__assert_rtn`, `__assert`,
`__stack_chk_fail`, `__chk_fail`, `__fortify_fail`, `err`, `errx`, `verr`,
`verrx`, `std::terminate`): nothing is cleared before it. `unwinds` marks a
call that unwinds the stack (`__cxa_throw`, `__cxa_rethrow`,
`_Unwind_RaiseException`, `_Unwind_Resume`, `_Unwind_Resume_or_Rethrow`,
`std::rethrow_exception` in both libraries' manglings): nothing is cleared
before it either. Every other call that does not return keeps today's
`__weavec_rt_unpoison_stack`. The name list `endsProcess` in
`GuardFrames.cpp` is deleted (AGENTS.md rule 9: library behavior lives in
the table). A row with either clause may have no parameters but `other`.

**The runtime marks the frames an exception unwound.** Per thread it keeps
`unwindLow`, the lowest stack address at which an exception in flight was
raised:

- The runtime interposes `_Unwind_RaiseException` and
  `_Unwind_Resume_or_Rethrow` (on ELF by its place in the search order and
  `dlsym(RTLD_NEXT, …)`, on Darwin by a `__DATA,__interpose` entry; for a
  `-static` link, by `-Wl,--wrap=` options the driver adds). The wrapper
  sets `unwindLow` to the minimum of its value and its own frame address
  and calls the real function. Every C++ throw, from guarded code or from
  the C++ library's shared object, goes through one of them.
- `__weavec_rt_landed()` writes the shadow of `[unwindLow, frame)`, where
  `frame` is its caller's frame address, as returned (`0xF5`), clamped to
  the thread's own stack, and resets `unwindLow` when called from a catch.
  The pass calls it at the start of every landing pad of a guarded
  function, with an argument saying whether the pad catches. The runtime
  also interposes `__cxa_begin_catch` the same way and calls it there, for
  catches in code built without WeaveC.
- RFC 0037 §9's `settle` then treats those granules as it treats a frame
  that returned: an access below the runtime's entry is a use after
  return; an access above it (a later frame of code without WeaveC that
  occupies the bytes) clears them.

The cost is proportional to the depth unwound and is paid only on the
exception path. A foreign exception, a forced unwind (`pthread_cancel` on
glibc) and an exception that ends in `std::terminate` take the same paths
or end the thread.

**`stackLostColors` is per-thread.** It is set only by
`__weavec_rt_unpoison_stack` (a `longjmp` and its kin) and stays in the
thread's runtime state.

`test/Guards/cxx-exceptions.cpp` pins the motivation's case (a live
caller's overflow after a throw stops), a pointer into an unwound frame
(`stack-use-after-return`), a throw from the C++ library's shared object
(`std::vector::at` on libstdc++, `std::stoi`), a callback from an
unguarded frame that reuses unwound bytes (no false trap: a custom
`streambuf` fed by `num_put`, `nftw`), rethrow, nested exceptions, and
`-static`.

### 4. `new` and `delete`

**The runtime defines the replaceable allocation functions**, in C under
their Itanium names: `operator new` and `operator new[]` with and without
`std::nothrow_t` and `std::align_val_t` (eight), and `operator delete` and
`operator delete[]` plain, sized, aligned, sized and aligned, and nothrow
(twelve). They are exported weak, as the C++ library's are, so a program's
own replacement still wins, and every image binds to the runtime's
otherwise (the dynamic loader's search order on ELF, weak coalescing on
Darwin).

- `new` and `new[]` allocate from the arena (aligned forms from its
  aligned path) and record the form in the block's metadata (two bits of
  its slot word, or of a huge block's header): `malloc`, `new` or
  `new[]`. `malloc`, `calloc`, `realloc`, `posix_memalign` and their kin
  record `malloc`.
- When the arena cannot serve a throwing form, the runtime calls the C++
  library's own `operator new` (found with `dlsym(RTLD_NEXT, …)`), which
  calls the runtime's `malloc` again, runs the program's new-handler, and
  throws `std::bad_alloc`; a block it returns is recorded as the form
  asked. The runtime itself never throws.
- A release checks the form: `free` and `realloc` release `malloc` blocks,
  `delete` releases `new` blocks, `delete[]` releases `new[]` blocks.
  A sized `delete` or `delete[]` also checks that its size is the block's
  requested size (for `delete[]` of an array with a cookie, the size the
  compiler passes includes it, as it does for `new[]`). A mismatch stops
  the program through `__weavec_rt_fatal` as an invalid release
  (*Diagnostics*).

The release paths keep RFC 0036's quarantine and RFC 0037's thread caches.

### 5. Containers

`runtime/weavec_asan.c` implements:

- `__sanitizer_annotate_contiguous_container(begin, end, oldMid, newMid)`:
  the granules of `[newMid, end)` become `0xFC` (container), the bytes of
  `[begin, newMid)` addressable in the heap block's color; a granule that
  `newMid` splits keeps its first `newMid & 15` bytes, as RFC 0037's
  partial granules do. Bytes outside the runtime's heap are left alone.
- `__sanitizer_annotate_double_ended_contiguous_container(begin, end,
  oldBegin, oldEnd, newBegin, newEnd)`: the same for a live range in the
  middle; a granule the front boundary splits stays addressable (the
  shadow encodes a prefix only), as ASan's does.
- `__sanitizer_verify_contiguous_container` and
  `__sanitizer_verify_double_ended_contiguous_container`: whether the
  shadow agrees (libc++'s debug mode calls them), and
  `__sanitizer_contiguous_container_find_bad_address`.

A guard that meets `0xFC` reports `container-overflow`. A release clears
the block's annotations with the block. `WEAVEC_RT_CONTAINERS=0` turns the
annotations into no-ops (A9).

### 6. The standard library's checks

- **libc++.** In the fast mode's default semantic, a failed check is
  `__builtin_verbose_trap`: an `llvm.trap` whose debug location is inlined
  at an artificial function named `__clang_trap_msg$<category>$<message>`.
  `GuardExpand` replaces each such trap in a guarded function by a call to
  `__weavec_rt_library_assertion(site, message)`, a slow path that reports
  `library-assertion` and traps (in `report` mode, reports once per site and
  continues, as a guard does). A trap without such a location is left
  alone. The verbose-abort semantic (`std::__libcpp_verbose_abort`) gets a
  table row with `wrapper(__weavec_rt_libcpp_verbose_abort)`.
- **libstdc++.** `_GLIBCXX_ASSERTIONS` calls `std::__glibcxx_assert_fail`
  (its file, line, function and condition) from inline header code: a
  table row redirects it to `__weavec_rt_glibcxx_assert_fail`, which
  reports `library-assertion` at the call's site with the condition as the
  message. On libstdc++ versions whose assertions are `__builtin_trap`
  without a message, they stay bare traps.

### 7. The C++ library's buffer members

The library table gains rows, by mangled name, for the members that the
headers of libc++ (`std::__1`) and of libstdc++ (`std::__cxx11`) leave to
the library's shared object and that take a raw buffer, for `char` and
`wchar_t` (`wide`): `basic_string`'s `append`, `assign`, `insert` and
`replace` from a pointer and a count or a string; `find`, `rfind`,
`find_first_of`, `find_last_of`, `find_first_not_of` and
`find_last_not_of` from a pointer and a count; `compare` with a pointer;
`copy` (its first byte, *Bugs deliberately not caught*); libc++'s
`__init(const value_type *, size_type)` and `__grow_by_and_replace`;
`basic_ostream::write`; and `basic_istream`'s `read`, `readsome`, `get`
and `getline` into a buffer. The implicit object is argument 0. Every row
gets RFC 0038 §2's audit: an exact-extent probe that runs clean and an
extent-plus-one probe that stops, on both libraries. The rows are listed in
the table at S4, generated from each library's extern-template lists
(libc++'s `__string/extern_template_lists.h`) and checked by a unit test
that demangles each name and matches it to its row's parameters.

### 8. The runtime, the passes and the ledger

- **The runtime** gains `runtime/weavec_cxx.c` (the allocation functions,
  the form checks, the unwinding interposers, `__weavec_rt_landed`, the
  library-assertion slow paths) and the container annotations in
  `weavec_asan.c`. Its interface version, `WEAVEC_RT_ABI`, becomes 39 (new
  entry points, a new shadow value). The export list and `weavec_rt.h`
  declare every new entry point. The runtime's line budget (AGENTS.md rule
  9) rises from 7,050 to 7,600 lines; the library's 9,000 stays.
- **Reports** print C++ function names demangled where they print a
  function (`WEAVEC_RT_BACKTRACE=1`), through the C++ library's
  `__cxa_demangle` when the process has one (found with `dlsym`).
- **The ledger** (`weavec-ledger` version 4) adds `display`, the demangled
  name, beside each row's `function` (the symbol). The summary line is
  unchanged.
- **Unsafe regions** keep working by source range: a template defined
  inside a `WEAVEC_UNSAFE` function or block is unsafe in every
  instantiation; a lambda inside one is unsafe; a member function takes
  `WEAVEC_UNSAFE` before its declaration as a function does. A function
  marked `no_sanitize("address")` (or `[[clang::no_sanitize("address")]]`)
  is unsafe as in C. `test/Guards/unsafe-region.cpp` pins them.

## Diagnostics

Two new report kinds:

```
weavec: container-overflow at <file>:<line>:<col>: <read|write> of <n> bytes at <address>
weavec: <address> is <k> bytes past the elements of a container in the <m>-byte heap object at <base>
```

```cpp
std::vector<int> v; v.reserve(8); v.push_back(1);
return v.data()[5];
```

```
weavec: library-assertion at <file>:<line>:<col>: <message>
```

where `<message>` is the C++ library's (`libc++ Hardening assertion __n <
size() failed: vector[] index out of bounds`, or libstdc++'s condition):

```cpp
std::vector<int> v(1);
return v[5];
```

Two new reasons of the existing invalid release report:

```
weavec: invalid release of <address>: allocated by <form> and released by <form>
weavec: invalid release of <address>: released by <form> with size <n> for a <m>-byte object
```

where `<form>` is `malloc`, `operator new`, `operator new[]`, `free`,
`realloc`, `operator delete` or `operator delete[]`. A use of an unwound
frame is the existing `stack-use-after-return`. One new environment
variable, `WEAVEC_RT_CONTAINERS=0` (§5). Each kind gets a `test/Guards/`
test pinning its lines, an entry in the command-line reference's list of
kinds, and an entry in `scripts/run-cases.py`'s `KINDS`.

## Implementation amendments

These record where the implementation departs from the design above. They
override the body.

1. **Darwin's system libraries release by another form (§4, the first
   unresolved question).** Measured at S3: Apple's `std::runtime_error`
   allocates its message with `operator new` and releases it with `free`,
   inside the system's libraries, so every caught `std::exception` stopped
   as an invalid release. On Darwin a release called from the dyld shared
   cache (the system's libraries; `_dyld_get_shared_cache_range`) and every
   release through the runtime's malloc zone take a block of any form; a
   release called from the program's own images is checked. Linux checks
   every release.
2. **Weak allocation functions and the Darwin archive (§4, the second
   unresolved question).** Confirmed: with the runtime's definitions weak,
   Darwin's loader binds every image's calls, the C++ library's own
   included, to them (a probe: every `delete` received a block of the
   runtime's `new`); with them strong, libc++'s dylib keeps its own. But
   ld64 then took the weak definitions from `libweavec_rt.a`, the fallback
   archive after the shared library (RFC 0038, amendment 11), and the
   program carried a second runtime. The Darwin archive therefore has no
   allocation functions: the runtime's C++ parts (`weavec_cxx.c`,
   `weavec_unwind.c`) are compiled once for the shared library and once,
   with `WEAVEC_RT_ARCHIVE`, for the archive. Darwin's typed allocation
   functions (`std::__type_descriptor_t`, used by `-ftyped-cxx-new-delete`)
   are not defined: the C++ library allocates through the plain forms, and
   a typed `new` and its typed `delete` are libc++abi's on both sides.
3. **Live slot words (§4).** A live slot's word is `size << 4 | form << 2
   | state`; a free or dead one's keeps `next << 2 | state`. The arena's
   largest class is 2^28 bytes (it was 2^30); a block of 256 MiB or more is
   a huge block, whose record holds its form.
4. **Marking unwound frames (§3).** `__weavec_rt_landed()` takes no
   argument. It marks `[unwindLow, frame)` and raises `unwindLow` to its
   frame, so a cleanup that resumes the unwinding has the frames above it
   marked from there (each byte is written once per exception); the
   interposer of `__cxa_begin_catch` marks up to the catching frame and
   resets `unwindLow`. Everything below the frame of the runtime's call is
   dead when it marks, so a mark never reaches a live frame, and one a
   later frame occupies is stale: `settle` clears it. The interposers are
   in `weavec_unwind.c`; a static C++ link (one with `-lstdc++` or `-lc++`)
   gets `--wrap` for the three and `-u __wrap__Unwind_RaiseException`.
5. **`library-assertion` stops in every mode (§6).** The C++ library's code
   after a failed check is unreachable, so report mode prints the report
   once per site and traps, as trap mode does. The message is the
   library's, without libc++'s leading `<file>:<line>: ` and its newline;
   libstdc++'s is the failed condition.
6. **Reports name the caller of system headers (§6, §8).** A report's
   location, a ledger row's and an unsafe region's skip the frames
   inlined from the unit's system headers, as they skip artificial
   functions: a check inlined from the C++ library's headers (a
   `library-assertion`, a guard inside `std::vector`) is reported at the
   line of the program that called it. The unsafe-region collector records
   the unit's system headers. A `WEAVEC_UNSAFE` or `no_sanitize` function
   inside a namespace, a class or a linkage specification is found too.
7. **Extern templates' inline bodies (§7).** With optimization the headers
   give `std::string`'s extern-template members an `available_externally`
   body, so their calls are calls of definitions the library pass skipped
   while the optimizer then called the shared object's copy. A row now
   governs a call of an `available_externally` function as of a
   declaration.
8. **The rows of §7** are listed by the generator kept with the
   assessment; they add each library's `_M_append` and `_M_replace`
   (libstdc++'s out-of-line workers) and libc++'s `__init` and
   `__grow_by_and_replace`, and give the implicit object its size (24 bytes
   for libc++'s strings, 32 for libstdc++'s) or, for a stream, its first
   byte. The unit test checks every row against an expectation table, as
   for C rows; the libc++ rows' audit is `test/Guards/cxx-string-rows.cpp`.
9. **Backtraces and fatal releases.** `WEAVEC_RT_BACKTRACE=1` prints one
   line per frame, `#n <pc> in <function> + <offset>`, C++ names demangled,
   after an invalid release too.
10. **libstdc++'s containers (§5, an unresolved question).** Measured on
    Ubuntu 24.04's libstdc++ 13: its vector annotations need
    `_GLIBCXX_SANITIZE_VECTOR` as well as `__SANITIZE_ADDRESS__`, so a C++
    compile also gets `-D_GLIBCXX_SANITIZE_VECTOR=1` unless its command line
    chooses it; it annotates no `deque`, so (K) holds for a `deque` with
    libc++ only, and the deque probe of §9's suite runs on Darwin
    (`REQUIRES: darwin`, a marker the case runner gains). Its assertion
    function is `__glibcxx_assert_fail`, whose message is the condition.
11. **Header-defined C++ library members (§7).** libstdc++ 13 in C++20
    defines `basic_string`'s `_M_append` and kin `linkonce_odr` in the unit,
    so the guards inside them caught an overflow, but at the header's line.
    A row of a C++ function (a mangled name) governs a call of a
    `linkonce_odr` definition as of a declaration: the call is checked at
    the program's line, and the body's accesses keep their guards.
12. **The allocation path (G6).** With the forms in, an allocation took one
    more call (the shared entry `weavecRtAllocForm` was not inlined) and a
    release asked for its caller's image: the allocation entry is inlined
    into `malloc`'s and the forms', and a release consults its caller only
    when the forms disagree.
13. **The inliner prices a marker as one instruction (G7).** Measured on
    the corpus's nlohmann/json workload (S7): a guarded build ran 4.4 times
    the reference, above ASan's 3.3, with the guards alone to blame
    (`-fweavec-checks=none` ran at 1.0): the inliner, which runs after
    `GuardInsert`, counted each marker as a call, so the lexer's `get()`,
    `vector::push_back` and their kin stayed out of line (357 functions in
    the binary against the reference's 166). ASan instruments after
    inlining and has no such cost. In a C++ unit the markers' declarations
    carry `"call-inline-cost"="5"`, the inliner's price of one instruction
    (`GuardOptions::cheapMarkers`, set from the unit's language): the
    workload runs at 2.4 times (213 functions). A price of nothing ran as
    fast but made nlohmann/json's largest test unit compile 1.3 times
    longer; 5 compiles it as before (8.8 s against 8.6 s). A C unit keeps
    the call's price: priced at 5, C inlined more and compiled 1.17 times
    v0.19.0's CPU (mujs 2.4 times, SQLite 1.5), against G8's 1.03.
14. **The corpus's C++ (§9, S7).** Measured at S7:
    - The gate gives every build `CXX` beside `CC` (the C++ twin of each
      compiler and wrapper), a config `language`, and a project
      `submodules` (LevelDB's and Snappy's googletest and benchmark at the
      commits their pins record) and `uses` (other checkouts a build
      reads, at `$CORPUS/<name>`: googletest for Abseil and ninja, Catch2
      for spdlog and CLI11, and two projects of test data,
      nlohmann/json's and simdjson's), so that nothing a build or test
      runs is downloaded. The motivation's STL program is the benchmark of
      a config, `stl`, carried by googletest's project. `gates.buildTime`
      and `gates.runTime` gain `cxx` limits for G8 and G7.
    - fmt's `write_to_ostream_max_size` hands `std::ostream::write` a null
      pointer and `PTRDIFF_MAX` (its mock stream buffer reads nothing),
      which §7's row stops: triaged as the project's bug, since `write`
      reads its characters from the array it is given.
    - Abseil, seeing `__SANITIZE_ADDRESS__` (RFC 0036, §5), builds its
      tests of AddressSanitizer itself, and the ones that test what WeaveC
      does not do as ASan does fail: death tests whose expected message is
      ASan's (its symbolized stack names `CrashIfIteratorIsInvalid`;
      WeaveC's report line names the line, and report mode, where a report
      does not kill, passes no death test), byte-exact
      `__asan_address_is_poisoned` of 8-byte slots and padding (WeaveC
      poisons whole granules), and annotations of `FixedArray`'s inline
      storage in a stack frame (§5 leaves bytes outside the heap alone).
      The config leaves them out by name (`GTEST_FILTER`); each one
      catches its bug or is a granule-size difference, and none is a false
      trap.
    - On linux-aarch64 yaml-cpp's tests initialize `char`s with negative
      constants, a narrowing error where `char` is unsigned, with either
      compiler; its build there turns the error into a warning.
    - DuckDB does not build against the macOS 27 SDK with either compiler:
      `<xlocale.h>`, which libc++ includes, now pulls in `<_langinfo.h>`,
      whose `ERA` macro breaks `DatePartSpecifier::ERA`. Its Darwin build
      undefines the macro first.
15. **`new[]`'s count under ASan's contract (§4; RFC 0036, §5).** With
    ASan's language option on, Clang's Itanium C++ ABI (Linux on both
    architectures; not Apple's arm64 ABI) stores the element count of an
    array of a type with a destructor through
    `__asan_poison_cxx_array_cookie` and reads it back through
    `__asan_load_cxx_array_cookie`, so DuckDB's executables did not link
    on Linux. The runtime defines both: the count is not poisoned (a release
    checks its form and its size, §4) and the load returns it.
    `test/Guards/cxx-new-delete.cpp` deletes such an array; the runtime
    made room within its 7,600 lines.
16. **A root whose shadow is uncolored now (RFC 0037 §8; S7).** On
    linux-aarch64 DuckDB stopped twice as `global-buffer-overflow` in its
    aggregate hash table, at an access through `entries` itself (0 bytes
    from the root). DuckDB allocates its buffers from its bundled jemalloc
    on Linux, memory the runtime does not own; when the inline check read
    the root's shadow it held a color (`0x1c`), and at the access it held
    none. What wrote that color was not found; a byte of untracked memory's
    shadow can hold one (a mapping that reuses addresses whose shadow was
    written), and a color check there has no object to compare. The slow
    path of a color check now passes when the root's shadow is uncolored
    at the access, as it does when it was uncolored when read.
    `rt_test`'s `stale-root-color` reproduces the report without it.
17. **DuckDB's IEJoin (§9, the programs tier; S7).** On linux-aarch64
    DuckDB's suite stopped as a `library-assertion` at
    `physical_iejoin.cpp:279`, a true bug: `GetStageNext` indexes
    `completed`, a `std::array` of `IEJoinSourceStage::DONE` elements, by
    the stage, and `TryPrepareNextStage` calls it once the stage is `DONE`,
    one element past the end. libstdc++'s assertions catch it when the
    join's threads finish in that order, so whether a run stops depends on
    timing, and amendment 5 stops the whole suite there. Every inequality
    join runs the operator (an ASOF join's tests stopped too), so no list
    of tests leaves it out: the programs tier's DuckDB build gives the array
    the missing element (it starts at zero, as the others do), as its
    Darwin build already edits a header for the SDK, and fails if the edit
    no longer applies. The corpus gate's list of report kinds gains
    `container-overflow` and `library-assertion`, which a triage entry
    could not name.
18. **Replaced allocation functions, failed allocations and deferred
    releases (§4; review of the PR).** Three faults of §4 as built:
    - A program that replaces some of the allocation functions (commonly
      only `operator new(size_t)` and `operator delete(void*)`) reached the
      runtime's other forms, which the C++ library's would have chained to
      the replacement: the sized `delete` Clang emits by default stopped
      as an invalid release, or released a block of the program's pool.
      The runtime now asks where the eight base forms (`new`, `new[]`,
      `delete`, `delete[]`, plain and aligned) resolve: the loader
      (`dlsym(RTLD_DEFAULT)`, since the Linux library binds its own calls
      to itself), or in a `-static` program the link, compared with the
      runtime's own definitions. When one is not the runtime's, each
      derived form calls its base as the library's do (a nothrow form the
      library's own nothrow form, which catches the base's
      `std::bad_alloc`; in a `-static` program its base), the runtime's
      base forms allocate as `malloc` and release any block, and no form
      is checked.
    - An allocation the arena could not serve went to the C++ library's
      form through `dlsym(RTLD_NEXT)`, which a `-static` program does not
      have, so every failure ended the program. The runtime now does what
      the library does: it runs the new-handler while there is one and
      retries (not for a nothrow form, whose handler's exception it could
      not catch), then returns null (nothrow) or throws `std::bad_alloc`
      through the library's own `__throw_bad_alloc`.
    - A release deferred while the thread holds an allocator lock kept its
      form in the pointer's low bits, so a misaligned, invalid pointer was
      released as the block's start. The form is kept beside the pointer,
      which is released as given.

    Cases `semantics/dropin/replaced-new_ok.cpp` and `failed-new_ok.cpp`
    pin the first two; the deferred path has no deterministic test (it
    needs a signal while a lock is held). The runtime's budget (AGENTS.md
    rule 9) rises from 7,600 to 7,700 lines: 7,698 with these.

## Drawbacks

- **Two libraries to track.** libc++ and libstdc++ differ in what they
  inline, how they name their members, how they report a failed check and
  which containers they annotate; §6 and §7 are per library and change
  with their versions.
- **Interposing the unwinder.** The runtime wraps two unwinder entry
  points and `__cxa_begin_catch` on every platform, with a third mechanism
  for `-static`. A future unwinder entry point would be missed until it is
  added.
- **Hardening changes behavior.** A program that reads `v[size()]` and
  never uses the value ran under Clang and now stops. That read is
  undefined behavior, and the macros can be overridden.
- **Form checks are strict.** Code that releases `new[]` with `delete` on
  a trivially destructible type ran with every allocator and now stops.
- **Build time.** C++ builds are about 1.65 times the reference's in the
  prototype, more than C builds pay.
- **CI time.** The corpus gains eight projects, four large programs and a
  sealed set.

## Alternatives

- **Do nothing for C++.** The precondition keeps excluding every program
  with a C++ unit, and the roadmap's next milestone waits.
- **Only lift the exclusion** (the prototype): C++ is guarded, but library
  calls under RAII are not, the first exception turns stack checks off,
  `<deque>` does not link with the ASan contract on, and hardening
  failures are silent.
- **ASan's `__cxa_throw` interception** (unpoison the whole stack at every
  throw): no interposition of the unwinder's entry points, but the loss
  the motivation measures.
- **Marking unwound frames without interposition**, from the landing pads
  alone, down to the stack's bottom: correct, but a write of up to an
  eighth of the stack's size (1 MiB of shadow for an 8 MiB stack) at every
  catch.
- **Instantiating the C++ library's string members in every unit** instead
  of rows: libstdc++ allows it (`_GLIBCXX_EXTERN_TEMPLATE`), libc++ 22 does
  not; and it would grow every unit's code and build time.
- **Wrappers for the C++ library's members** in the runtime: C calling
  C++ members by their manglings, with each member's semantics duplicated;
  rows need neither.
- **No form checks**, keeping `new` on `malloc`: no runtime code, but the
  most common C++ allocator misuse stays silent.
- **Programs' own allocators** (a CPython run with 515,611 live Python
  objects made 2,337 allocations from the runtime: pymalloc serves the rest
  from memory the runtime does not track), **exact spatial checks**, **deterministic use after return** and
  **Windows**: considered in the assessment and left for later RFCs
  (*Future work*); each is independent of C++.

## Prior art

- **AddressSanitizer** guards C++ with the same instrumentation as C,
  intercepts `__cxa_throw` to unpoison the stack (`asan_interceptors.cpp`,
  `__asan_handle_no_return`), replaces the allocation functions and
  reports `alloc-dealloc-mismatch` (on by default on Linux, off on Darwin)
  and `new-delete-type-mismatch`, and defines the container annotation
  interface that libc++ and libstdc++ call (`container-overflow`, with the
  same mixed-build limitation, `detect_container_overflow=0`).
- **libc++ hardening** (LLVM 18 and later: none, fast, extensive and debug
  modes; assertion semantics in recent releases) and **libstdc++'s
  `_GLIBCXX_ASSERTIONS`**, on in Fedora's default package flags: bounds checks
  without a runtime. Clang's `__builtin_verbose_trap` carries their
  messages in debug information, which §6 reads.
- **Valgrind's memcheck** also tells `new[]` from `new` and `malloc`
  (mismatched free) by replacing the allocation functions.

## Unresolved questions

(Amendments 1, 2 and 10 settle the first, the second and the third.)

- **Darwin's system libraries and the form checks.** ASan turns
  `alloc-dealloc-mismatch` off on Darwin; whether a system framework
  mismatches forms in a process whose allocation functions are the
  runtime's is measured at S4. If one does, the check on Darwin applies
  only to releases called from images built by `weavec-cc` (the runtime
  knows them), recorded as an amendment.
- **Weak coalescing** of the allocation functions on Darwin with the
  runtime as a dependency of the executable (§4): confirmed at S4 with a
  program that replaces `operator new` and a library that calls it.
- **libstdc++'s assertion function** across the versions on the gate's
  runners (13 and 14 call `__glibcxx_assert_fail`; older ones may trap or
  abort), and whether its vector annotations (`_GLIBCXX_SANITIZE_VECTOR`)
  turn on under `__SANITIZE_ADDRESS__` alone.
- **The C++ library's string members for libstdc++'s old ABI**
  (`_GLIBCXX_USE_CXX11_ABI=0`): rows are added only if a corpus project
  uses it.
- **The C++ corpus's pins and benchmarks**, chosen at S0 by what builds
  with CMake and runs its suite without a network on all three platforms.

## Future work

- Objective-C and Objective-C++ (ARC, blocks, message sends).
- Programs' own allocators: honoring Valgrind's client requests for
  pools, a runtime statistic of untracked heap, and documented switches to
  the C allocator (CPython's `PYTHONMALLOC=malloc`, Redis's `MALLOC=libc`).
- Checking a container's logical extent for `std::string` when the C++
  library is built for it, and `std::map`/`std::unordered_map` node
  lifetimes.
- From RFC 0037's and RFC 0038's *Future work*: concurrent marking,
  hardware tags, colors carried by moved pointers, Windows.
